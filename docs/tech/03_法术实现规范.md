# 法术实现规范

> 本文规定 16 个记忆法术的实现方式、数据存储、以及三个核心子系统的技术方案。
> 上级：[README 总览](../README.md)　｜　相关：[01 ISS API 参考](01_ISS官方API参考.md)、[04 法术等级强度表](04_法术等级强度表.md)

## 一、法术类的最小结构

每个法术是一个继承 `AbstractSpell` 的类，必须提供四样东西：

| # | 内容 | 说明 |
|---|---|---|
| ① | `spellId` 字段 | `new ResourceLocation("mnemosyne", "mnemonic_bolt")` |
| ② | `defaultConfig` 字段 | `DefaultConfig`，在构造器里链式构建 |
| ③ | 数值字段 | `baseManaCost` / `manaCostPerLevel` / `baseSpellPower` / `spellPowerPerLevel` / `castTime` |
| ④ | 四个覆写 | `getSpellResource()` / `getDefaultConfig()` / `getCastType()` / `onCast(...)` |

### 构造器里的赋值顺序（对照官方写法）

官方法术的构造器统一是：先赋 `spellId`，再赋 `defaultConfig`（调用 `getDefaultConfig()` 构建），最后赋五个数值字段。**顺序不影响功能**，但保持与官方一致便于对照。

### 官方参照值（用于校准，反编译提取）

| 法术 | maxLevel | minRarity | baseMana | manaPerLv | basePower | powerPerLv | castTime | 冷却 |
|---|---|---|---|---|---|---|---|---|
| Firebolt | 10 | Common | 10 | 2 | 12 | 1 | 0（INSTANT） | 0.5s |
| Fireball | 5 | — | 60 | 15 | 1 | 1 | 40（LONG） | 25s |
| Shield | 10 | — | 35 | 5 | 5 | 10 | 0 | 8s |
| Counterspell | 1 | — | 50 | 1 | 1 | 1 | 0 | 10s |

> **观察**：官方法术的 `maxLevel` 并不统一（10 / 5 / 1）。
> 记忆流派统一用 **`maxLevel = 5`**，理由是 5 个等级恰好一一对应 5 档稀有度（见 [01 文档 §七](01_ISS官方API参考.md) 示例 A）。

## 二、数值计算的三条公式（实现时必须遵守）

```
法力  = (baseManaCost + manaCostPerLevel × (level − 1)) × MANA_MULTIPLIER
威力  = (baseSpellPower + spellPowerPerLevel × (level − 1)) × SPELL_POWER × 学派强度 × POWER_MULTIPLIER
冷却  = cooldownInSeconds × 20  （tick，与等级无关）
```

### 关键实现约定

| 约定 | 说明 |
|---|---|
| **威力是"抽象威力"，不是伤害** | `getSpellPower()` 返回的是经过三层乘算的浮点值。具体造成多少伤害，由法术自己在 `onCast` 里乘以一个**系数**决定 |
| **伤害系数写在哪** | 建议每个法术写一个私有方法 `getDamage(int level, LivingEntity caster)`，内部调用 `getSpellPower(level, caster)` 再乘系数。这样官方公式改动时只需改一处 |
| **不要硬编码伤害数字** | 硬编码会导致 `memory_spell_power` 属性完全失效，平衡崩盘 |
| **冷却不随等级变化** | 官方如此设计。若想让高等级冷却更短，需覆写 `getSpellCooldown()` |

## 三、三种基类设计（减少重复代码）

16 个法术中有大量共享逻辑。建议抽出 3 个抽象基类：

### 3.1 `EncodeSpell`（写入类基类）

适用于：术忆、质忆、痛忆、记忆掠夺（4 个）

**共享逻辑**：

1. 检查是否有空忆格 → 无则中断并提示
2. 找到第一个空忆格
3. 构造对应的 `MemoryEntry` 子类
4. 写入 + 设置 `expireTick`
5. 播放"抽取"粒子（丝线从目标/自身飞向施法者）
6. 同步忆格数据到客户端

**子类只需实现**：`buildEntry(level, caster, target)` —— 构造具体要写入的记忆内容。

**注意**：写入失败时是否消耗法力，由 `checkPreCastConditions` 决定。
建议**术忆/质忆无目标时不消耗法力**（`checkPreCastConditions` 返回 false），**但忆格满时消耗法力**（这是刻意的惩罚）。

### 3.2 `OblivionSpell`（遗忘类基类）

适用于：遗忘、失忆、遗忘诅咒、集体遗忘（4 个）

**共享逻辑**：

1. 通过 `OblivionRegistry` 查表得到目标的"可遗忘能力清单"
2. 按子类策略选择要移除的能力
3. 施加「失忆」状态效果（携带被移除目标的记录，用于恢复）
4. 对 BOSS 走降级分支

**子类只需实现**：`selectAbilities(target, registry)` —— 选哪些能力移除。

### 3.3 `MnemosyneProjectileSpell`（投射物法术基类）

适用于：忆矢（1 个，但预留扩展）

**共享逻辑**：生成投射物 → 设置伤害 → 设置拖尾粒子 → 命中时给目标叠认知过载。

> **重要**：ISS 的 `AbstractMagicProjectile` **不在 api 包内，编译期不可见**。
> 我们必须**自己写投射物基类**（继承原版 `Projectile` 或 `AbstractArrow`），
> 并实现 `api.entity.NoKnockbackProjectile` 接口来获得"不产生击退"的行为。

### 3.4 `MnemosyneLongCastSpell`（长吟法术基类）⭐

适用于：记忆掠夺、忆海、千忆归一（3 个 `LONG` 类型法术）。

**背景**：见 `04_法术等级强度表.md` §〇 更正 1 —— ISS 的 `CastType` **没有 `CHARGE`**，
只有 `NONE` / `INSTANT` / `LONG` / `CONTINUOUS`。三个"大招"必须用 `LONG`，
且 `LONG` 的 `castTime` 是**固定值**（除非覆写 `getCastTime(level)`）。

**ISS 给 `LONG` 类型提供的两个钩子**（实测自 `AbstractSpell`）：

```java
public abstract CastType getCastType();
public int getCastTime(int spellLevel);
public int getEffectiveCastTime(int spellLevel, LivingEntity entity);
public void onCast(Level, int spellLevel, LivingEntity entity, CastSource, MagicData);
public void onServerCastTick(Level, int spellLevel, LivingEntity entity, MagicData);  // ⭐ 关键
```

`onServerCastTick` **在吟唱期间的每一 tick 被调用**（服务端）。这是实现
"吟唱期选择机制"和"忆格点燃"的唯一入口。

**基类骨架**：

> **⚠️ 下面这段骨架里的 `super(config)` 是错的，编译不过**（Phase 2 实测，2026-09-15）。
> 实测 `AbstractSpell` **只有一个无参构造器**（源码逐字：`public AbstractSpell() {}`）。
> 正确写法见 §3.5 —— 自己 `super()`，把 config 存成字段，覆写 `getDefaultConfig()`。

```java
public abstract class MnemosyneLongCastSpell extends AbstractSpell {

    protected MnemosyneLongCastSpell(DefaultConfig config) { super(config); }   // ❌ 编译不过

    @Override
    public CastType getCastType() { return CastType.LONG; }

    /** 各法术覆写：吟唱时间随等级递减 */
    @Override
    public int getCastTime(int spellLevel) {
        return defaultCastTime();   // 子类提供基准值
    }

    protected abstract int defaultCastTime();

    /**
     * 吟唱期逐 tick 逻辑。
     * 注意：这个方法的 spellLevel 参数是「施法时的等级」，吟唱期间不变。
     */
    @Override
    public void onServerCastTick(Level level, int spellLevel, LivingEntity entity, MagicData magicData) {
        if (!(entity instanceof ServerPlayer player)) return;

        // 1. 计算吟唱进度（0.0 ~ 1.0）
        float progress = computeCastProgress(player, magicData);

        // 2. 子类处理逐 tick 效果（切换选中目标 / 点燃忆格 / 领域预告）
        onLongCastTick(player, spellLevel, progress, magicData);

        // 3. ⚠️ 2026-09-17 起无 HUD：进度表现改走服务端粒子（SpellFeedback.channelTick）
        MnemosyneNetwork.syncCastProgress(player, progress, getSelectedIndex(player));
    }

    /** 子类实现：吟唱期的具体逻辑 */
    protected abstract void onLongCastTick(ServerPlayer player, int spellLevel,
                                           float progress, MagicData magicData);

    /** 子类实现：吟唱完成时的结算 */
    protected abstract void onLongCastFinish(ServerPlayer player, int spellLevel);

    @Override
    public void onCast(Level level, int spellLevel, LivingEntity entity,
                       CastSource source, MagicData magicData) {
        if (entity instanceof ServerPlayer player) {
            onLongCastFinish(player, spellLevel);
        }
        super.onCast(level, spellLevel, entity, source, magicData);
    }
}
```

**⚠️ 吟唱进度的获取是个坑**：`MagicData` 里的吟唱计时字段不在 api 包内。
实测可行的两种做法：

| 做法 | 说明 | 评价 |
|---|---|---|
| **A. 自己计时**（推荐） | 在 `SpellPreCastEvent` 里记录 `player.getUUID() → startTick`，`onServerCastTick` 里用 `player.tickCount - startTick` 算进度 | 零反射，完全可控 |
| B. 反射读 `MagicData` 的私有字段 | 字段名在版本间会变 | ❌ 不推荐 |

做法 A 的骨架：

```java
public final class LongCastTracker {
    private static final Map<UUID, Integer> START_TICKS = new ConcurrentHashMap<>();

    public static void begin(ServerPlayer player) {
        START_TICKS.put(player.getUUID(), player.tickCount);
    }

    /** 返回吟唱已进行的 tick 数；未在吟唱中返回 -1 */
    public static int elapsed(ServerPlayer player) {
        Integer start = START_TICKS.get(player.getUUID());
        return start == null ? -1 : player.tickCount - start;
    }

    public static void end(ServerPlayer player) {
        START_TICKS.remove(player.getUUID());
    }
}
```

在 `SpellPreCastEvent` 里对忆海学派的长吟法术调 `LongCastTracker.begin(player)`，
在 `onServerCastTick` 里调 `elapsed(player)`，在吟唱结束/取消时调 `end(player)`。

**三个长吟法术的具体机制**（见 `06_法术_高阶_Epic与Legendary.md`）：

| 法术 | 吟唱期机制 | 实现要点 |
|---|---|---|
| **记忆掠夺** | 列出目标全部特性，按 `Z` 循环切换选中项 | ⚠️ 2026-09-17 起无 HUD：特性列表走聊天栏；选中项仍需 C2S 包 + 服务端校验（未实现，WS-E2） |
| **忆海** | 忆晶碎片粒子逐步聚集，环形进度条收缩 | 纯客户端演出，服务端只发进度 |
| **千忆归一** | 忆格逐格"点燃"（每 0.25s 一格） | 服务端按进度点亮，被打断时**不消耗**忆格 |

**⚠️ 打断处理**：吟唱被打断时，ISS 会**不再调用** `onServerCastTick`。
所以你**不能**依赖"最后一 tick"来清理状态。正确做法是在
`SpellPreCastEvent` 的配对清理点 + `PlayerTickEvent` 里做**超时兜底**：

```java
@SubscribeEvent
public void onPlayerTick(PlayerTickEvent.Post event) {
    if (!(event.getEntity() instanceof ServerPlayer player)) return;
    int elapsed = LongCastTracker.elapsed(player);
    // 超过最长吟唱时间仍未结束 → 判定为被打断，清理
    if (elapsed > MAX_LONG_CAST_TICKS) {
        LongCastTracker.end(player);
        onLongCastInterrupted(player);
    }
}
```

### 3.5 实际交付的基类层次（Phase 2 · WS-C，2026-09-15）

```
io.redspace.ironsspellbooks.api.spells.AbstractSpell      ← ISS 的
   │
   └── MnemosyneSpell                    ← ⭐ WS-C 新增的公共父类
         │                                  持有 DefaultConfig / 伤害公式 / 学派伤害源
         ├── EncodeSpell                  → getCastType() = LONG
         ├── OblivionSpell                → getCastType() = INSTANT
         ├── MnemosyneProjectileSpell     → getCastType() 仍抽象，由子类决定
         └── MnemosyneLongCastSpell       → getCastType() = LONG（final 锁死）
```

**为什么比 `tech/11` §七 的清单多了一层 `MnemosyneSpell`**：
`tech/10` §九 的反模式清单写了"让 WS-D1/D2/D3 共用一个文件放公共逻辑 → 公共逻辑上提到 WS-C 的基类"。
16 个法术共享「持有 config」「按公式算伤害」「用学派伤害源打伤害」这三件事，
上提到一个公共父类比在 4 个基类里各写一遍干净。**这是新增，不是修改** ——
下游仍然只 `extends` 那四个具名基类，契约不变。

**⭐ 唯一正确的 config 写法**（因为 `AbstractSpell` 只有无参构造器）：

```java
public abstract class MnemosyneSpell extends AbstractSpell {
    private final DefaultConfig defaultConfig;

    protected MnemosyneSpell(DefaultConfig defaultConfig) {
        super();                                  // ✅ 无参
        this.defaultConfig = defaultConfig;
    }

    @Override
    public final DefaultConfig getDefaultConfig() { return defaultConfig; }
}
```

**⭐ 伤害必须这样算**（否则 `baseSpellPower` 会被算两次）：

```java
// 正确：基础威力 × 系数 × 施法者加成倍率
float dmg = basePowerOf(level) * 系数 * powerMultiplierOf(level, caster);
// 等价写法（系数已含在抽象威力里时）
float dmg = powerOf(level, caster) * 系数;
```

`powerOf(level, caster)` = `getSpellPower(...)` =
`(baseSpellPower + spellPowerPerLevel×(level-1)) × SPELL_POWER × 学派强度 × POWER_MULTIPLIER`。
**它已经把 `baseSpellPower` 含进去了**，所以再乘一次 `basePowerOf` 就是重复计算。

### 3.6 三个"接口缝"（让 Phase 2 的四条线能真正并行）

WS-C 的基类**刻意不直接依赖**其他工作流的类，而是留可覆写的钩子：

| 基类 | 钩子 | 现在返回什么 | 谁来接 |
|---|---|---|---|
| `EncodeSpell` | `hasFreeEngramSlot(ServerPlayer)` | `true` | **WS-B** 忆格数据层 |
| `EncodeSpell` | `syncEngrams(ServerPlayer)` | 空实现 | **WS-B** 网络同步 |
| `OblivionSpell` | `oblivionManager(caster, target, tier)` | `false` | **WS-E** 遗忘系统 |
| `OblivionSpell` | `isOblivionImmune(target)` | 血量 ≥100 的怪物（临时启发式） | **WS-E** `AbilityMap.isBoss` |
| `OblivionSpell` | `applyBossFallback(...)` | 空实现 | **WS-E2** BOSS 降级 |
| `MnemosyneProjectileSpell` | `onProjectileHit(...)` | 完整实现（可直接用） | **WS-J** 投射物实体来调用它 |

**为什么这么做**：如果 WS-C 直接 `import capability.MnemosyneData`，
那么在 WS-B 交付之前整个 `spell/base/` 都编译不过，Phase 2 的四条线就退化成串行。
留钩子的代价只是每个钩子上有一行 `TODO(WS-X)`。

## 四、伤害来源：必须走 `SpellDamageSource`

### 4.1 为什么

`AbstractSpell.getDamageSource(Entity caster)` 返回一个 `SpellDamageSource`。
这个类携带了**学派信息**，ISS 的伤害管线据此：

1. 读取目标的 `memory_magic_resist` 做减免
2. 读取目标的 `SPELL_RESIST` 做全局减免
3. 触发 `SpellDamageEvent`
4. 让伤害被 `Counterspell` 等机制正确识别

**如果直接用原版 `DamageSource`，上述全部失效**，`memory_magic_resist` 形同虚设。

### 4.2 实现要点

| 要点 | 说明 |
|---|---|
| 取伤害源 | `getDamageSource(caster)` 或 `getDamageSource(caster, directEntity)` |
| 投射物伤害 | 在投射物的命中回调里，用**施法者**（不是投射物）去取伤害源 |
| 真实伤害 | 「认知崩坏」需要无视护甲。做法：先用 `SpellDamageSource` 造成伤害，再单独处理护甲穿透；**不要**直接改原版伤害类型 |
| 伤害上限 | 「痛忆」有 60% 最大生命上限，在计算阶段截断 |

## 六、忆格系统（核心技术难点）

### 6.1 存储方案选择

**1.20.1 Forge 没有 `AttachmentType`**（那是 NeoForge 1.20.4+ 的 API）。可选方案：

| 方案 | 优点 | 缺点 | 推荐 |
|---|---|---|---|
| **`player.getPersistentData()`（ForgeData NBT）** | 随玩家存档自动保存、无附加失败风险、已在生产环境验证 | 需要手动清理（死亡时） | ⭐ **首选** |
| Forge Capability | 生命周期清晰 | 在复杂整合包里偶发"服务端玩家没有能力"的问题 | 备选 |

> **推荐 `getPersistentData()`**：直接存 NBT，读写简单，且能规避整合包环境下的能力附加失败。
> 参照已投产 addon 的做法——它正是因为踩过这个坑才改用 `getPersistentData()`。

### 6.2 数据结构

```
NBT 根键：mnemosyne_engram

{
  slots: [                      // 定长数组，长度 = 当前忆格上限（3~5）
    { type: "spell", spellId: "irons_spellbooks:fireball", level: 3, power: 1.0, expire: 2400 },
    { type: "trait", traitId: "fire_immunity", duration: 600, expire: 2400 },
    { type: "pain",  amount: 12.0, expire: 2400 },
    null,                       // 空忆格
    null
  ],
  tempSlots: 0,                 // 临时忆格数量（碎忆 / 忆格扩张）
  permSlots: []                 // 记忆掠夺写入的永久记忆（不腐坏）
}
```

### 6.3 三种记忆条目的字段

| 类型 | 字段 | 说明 |
|---|---|---|
| `spell`（术忆） | `spellId`、`level`、`power` | `power` 记录写入时的威力快照 |
| `trait`（质忆） | `traitId`、`duration` | `traitId` 对应 `TraitRegistry` 的键 |
| `pain`（痛忆） | `amount` | 记录的伤害总量（已截断到上限） |

### 6.4 写入与释放流程

**写入**（由 `EncodeSpell` 基类统一处理）：

```
① 检查空忆格（常驻 + 临时）
② 无空位 → 中断，提示 "忆格已满"
③ 构造 MemoryEntry
④ expireTick = 当前 tick + 有效期（默认 2400 tick = 120 秒）
⑤ 写回 NBT
⑥ 发送 S2C 同步包
⑦ 播放抽取粒子 + 音效
```

**释放**：

```
① 选择忆格（默认先进先出；有忆晶权杖时可选任意）
② 读取 MemoryEntry
③ 按类型分派：
     spell → 调用 AbstractSpell.castSpell(...) 执行，威力 × 0.7 × 共鸣加成
     trait → 给玩家施加对应属性修正 / 状态效果
     pain  → 对目标造成伤害（走 SpellDamageSource）
④ 清空忆格（"复诵"法术除外）
⑤ 同步 + 播放破碎粒子
```

### 6.5 腐坏计时

在 `PlayerTickEvent` 里：

```
每 tick：
    如果 tick % 20 == 0（每秒检查一次，降低开销）：
        遍历忆格
        如果 expireTick <= 当前 tick：清空该格 + 播放碎裂音效 + 同步
        否则如果剩余 < 20 秒：标记为"即将腐坏"（客户端闪烁）
```

> **性能注意**：不要每 tick 都遍历并发包。**只在状态真正改变时发包**。
> 倒计时的"剩余时间"可以让客户端自己按已同步的 `expireTick` 推算，不需要每秒同步。

### 6.6 死亡清空

监听 `LivingDeathEvent`，如果是玩家 → 清空忆格 NBT + 同步。

> **注意**：`getPersistentData()` 在死亡后**不会自动清空**（它跟着玩家走）。必须显式清。

### 6.7 临时忆格

| 来源 | 数量 | 时长 |
|---|---|---|
| 碎忆 | +1 | 15s（满级 40s） |
| 忆格扩张 | +2 | 30s（满级 60s） |
| 忆海领域 | +3 | 8s（满级 15s） |

**到期时若其中有记忆 → 记忆一并消散**（这是刻意的风险设计）。

实现：用 `tempSlots` 计数 + 每个临时格独立的 `expireTick`。到期时先清内容再减计数。

## 七、遗忘系统（工作量最大）

### 7.1 三张映射表

| 表 | 用途 | 结构 |
|---|---|---|
| `OblivionRegistry` | 可被遗忘的能力 | 生物类型 → 能力列表 |
| `TraitRegistry` | 可被窃取的特性 | 生物类型 → 特性列表 |
| `MimicRegistry` | 可被复现的技能 | 生物类型 → 对应法术 |

**建议做成数据包可覆盖**：监听 `AddReloadListenerEvent`，从 `data/mnemosyne/mnemosyne/oblivion/*.json` 读取，
这样整合包作者可以不改代码就补充生物。

### 7.2 移除 AI 行为的正确做法

**1.20.1 的相关 API（Mojang 官方映射）**：

| 类 | 成员 | 说明 |
|---|---|---|
| `Mob` | `goalSelector` | **protected**，行为选择器（移动、攻击、跳跃） |
| `Mob` | `targetSelector` | **protected**，目标选择器（追击） |
| `GoalSelector` | `addGoal(int priority, Goal goal)` | 添加 |
| `GoalSelector` | `removeGoal(Goal goal)` | 移除 |
| `GoalSelector` | `getAvailableGoals()` | 返回 `Set<WrappedGoal>` |
| `WrappedGoal` | `getGoal()` / `getPriority()` / `isRunning()` / `stop()` | 访问内部信息 |

**⭐ 更正（2026-09-16 实测）：`goalSelector` 在 1.20.1 Forge 下是 public 的，不需要 Mixin、不需要反射。**

原文写的是"`goalSelector` 是 protected，需要 Accessor Mixin 或反射"。**这是错的。**
实测把下面这段代码放进工程，`./gradlew compileJava` **直接通过**：

```java
GoalSelector gs = mob.goalSelector;              // ✅ 可访问
GoalSelector ts = mob.targetSelector;            // ✅ 可访问
for (WrappedGoal w : gs.getAvailableGoals()) {
    Goal goal = w.getGoal();                     // ✅
    int priority = w.getPriority();              // ✅
    boolean running = w.isRunning();             // ✅
    gs.removeGoal(goal);                         // ✅
    gs.addGoal(priority, goal);                  // ✅
    w.stop();                                    // ✅
}
```

原因：**Forge 的 AccessTransformer 把 `Mob.goalSelector` / `targetSelector` 提升成了 public**，
在 MCP 的 `AccessTransformer` 步骤就写进了编译期的类签名，运行时由 Forge coremod 同样应用。
（`javac` 对 `protected` 是严格检查的 —— 能编译通过就证明它确实是 public。）

**影响**：§7.3 的"方案 B（Mixin 拦截 `canUse()`）"整段作废，
不需要按生物分 P0/P1 两套方案，**统一用方案 A（移除 + 记录 + 到期恢复）** 即可。
WS-E 因此**不需要引入 Mixin 的构建配置**（`mixins.json` + refmap + annotation processor），
从"全项目最大技术风险"降级为"量大但直白"。

### 7.2.1 ⚠️ 更正二：有 6 个生物**没有 goal**，方案 A 对它们无效（2026-09-17 实测）

`goalSelector` 虽然可访问了，但**不是所有生物都用 `GoalSelector`**。

**实测方法**（可复现）：从 Forge 反编译 jar
`forge-1.20.1-47.4.0-decomp.jar` 读各生物源码，搜索 `m_25352_`
（即 `GoalSelector.addGoal` 的 SRG 名）：

| 生物 | goal 数 | AI 实现 |
|---|---|---|
| 监守者 `warden` | **0** | `Brain` + `ai.behavior.warden.SonicBoom` |
| 山羊 `goat` | **0** | `Brain`（Ram 行为） |
| 猪灵 `piglin` / `piglin_brute` / `zoglin` / `hoglin` | **0** | `Brain` |

其余 33 个在能力表里的生物 goal 数正常（如僵尸 12、唤魔者 18、凋灵骷髅继承僵尸 12）。

**后果（这是会静默失效的那一类）**：
`presentAbilities(warden)` 恒为空 → 走通用降级 → **遗忘对监守者完全无效**，
但编译通过、无报错。而 `docs/02` §五 案例 3 把"遗忘监守者"写成了流派的高光时刻。

**应对**（已在 WS-E 落地，2026-09-17）：
- `AbilityMap.BRAIN_MOBS` 显式列出这 6 个生物；
- `AbilityMap.removalSupported(EntityType)` 返回 `false`，法术/UI 据此调整文案，
  不要向玩家承诺"让监守者忘记声波"；
- `AbilityMap.presentAbilities()` 对它们短路返回空 → 明确走降级；
- `tools/check_mob_goals.py` 拿反编译 jar 逐生物核对，防止将来漏报/误报。

**为什么不在这里修**：改 `Brain` 需要动它的私有 `memories`/`behaviors`，
而 `Brain` **没有**被 Forge 的 AccessTransformer 提升（`goalSelector` 被提升了，`Brain` 没有），
只能走 Mixin 或反射 —— 而 Mixin 已被明确排除。
正确的 Brain 门控方案属于 **WS-E2**，不要在这里做半成品。

**附：女巫的"喝药"同理不可遗忘。** 实测 `Witch.java` 只有
`FloatGoal` / `RangedAttackGoal` / 两个游荡与观察 goal，
**没有**喝药 goal —— 喝药是 `aiStep()` 里的内联逻辑（血量低时直接给自己灌药）。
所以 `docs/02` §五 案例 2 的"失忆 → 女巫 4 秒内既不能喝药也不能扔药"
**只有"不能扔药"能实现**（靠移除 `RangedAttackGoal`），"不能喝药"做不到。
这条差异必须让玩家可见（法术文案），否则会被当成 bug。

### 7.3 临时移除 vs 永久移除 —— 这是最容易出错的地方

`removeGoal()` 是**永久**的。但"遗忘"必须是**临时**的（6 秒后要恢复）。

**方案 A：移除 + 记录 + 到期恢复**（通用，但有风险）

```
遗忘时：
    遍历 getAvailableGoals()
    找到匹配的 WrappedGoal
    记录 { goal 实例, priority } 到状态效果 NBT
    removeGoal(goal)

到期时：
    从 NBT 读回 { goal, priority }
    addGoal(priority, goal)
```

- **优点**：通用，不需要为每个生物写代码
- **风险**：① 恢复后行为的**内部状态**可能已重置；② 恢复的 `Goal` 实例可能与新添加的行为冲突；③ 若期间生物死亡，NBT 记录无意义（无害）

**方案 B：Mixin 拦截 `canUse()`**（⭐ **已作废，2026-09-16**）

```
Mixin 到目标行为类（例如 Blaze 的火焰攻击行为）
    canUse() / canContinueToUse():
        如果 owner 身上有「失忆」效果 → return false
```

- **优点**：行为实例不被动过，恢复时**完全无副作用**
- **缺点**：每个生物的能力类都要写一个 mixin
- **作废理由**：见 §7.2 的更正 —— 方案 A 需要的 API 全部可直接调用，不需要 Mixin。
  为了一个已经能干净解决的问题去引入 Mixin 构建链，是纯粹的额外风险。

**结论：统一用方案 A（移除 + 记录 + 到期恢复），不按生物分档。**

> ⚠️ 方案 A 的三个已知风险仍然存在，必须在实现时处理：
> ① 恢复后行为的**内部状态**可能已重置（例如已充能的攻击要重新蓄力）；
> ② 恢复的 `Goal` 实例可能与期间新添加的行为冲突（恢复前先查一遍是否已在列表里）；
> ③ 若期间生物死亡，NBT 记录无意义（丢弃即可，无害）。

### 7.4 通用降级（必须实现）

对于**没有单独映射**的生物（含其他模组生物），统一降级：

| 法术 | 降级效果 |
|---|---|
| 遗忘 | 目标受到的伤害 +10%，持续 6 秒 |
| 失忆 | 目标停止攻击 1.5 秒 |
| 集体遗忘 | 目标移速 -20%，持续 6 秒 |
| 写入 · 质忆 | 写入"通用记忆"：释放时获得 +10% 移速 30 秒 |
| 走马灯 | 复现失败，返还 50% 法力 |

> **降级必须存在**，否则装了其他模组的玩家会发现记忆流派完全失效。

### 7.5 状态效果承载

「失忆」「遗忘」「迟滞」「认知过载」都是自定义 `MobEffect`。

| 效果 | 承载的数据 | 实现要点 |
|---|---|---|
| **认知过载** | 层数（用 `amplifier`） | 在伤害计算事件里按层数乘算记忆伤害 |
| **失忆** | 被移除的行为记录（NBT） | 到期时恢复；对玩家无效（`isDurationEffectTick` 里判断） |
| **遗忘** | 被移除的行为记录（NBT） | 同上 |
| **迟滞** | 无 | 通过属性修正降低攻击速度与移速 |

> **效果对玩家无效的处理**：在 `MobEffect.applyEffectTick(LivingEntity, int)` 或 `isDurationEffectTick` 里判断
> `entity instanceof Player` → 直接 `removeEffect`。这样即使被误施加也会立刻消失。

## 八、特性窃取

### 8.1 三类特性

| 类别 | 实现方式 | 例子 |
|---|---|---|
| **被动免疫类** | 监听对应伤害事件并 `cancel()` 或减免 | 火焰免疫、凋零免疫、缓降 |
| **属性修改类** | 施加临时 `AttributeModifier` | 速度、跳跃、抗击退、夜视 |
| **主动能力类** | 注册一个按键/法术入口 | 爬墙、短距传送 |

> **实现顺序建议**：先做前两类（简单、覆盖 80% 的特性），第三类放到后期。

### 8.2 属性修改类

用 `AttributeModifier` + `AttributeInstance.addTransientModifier(...)`，到期时 `removeModifier(...)`。

- 必须用**瞬态修饰符**（transient），避免被存档永久保留
- 用一个固定 UUID 作为修饰符 id，重复施加时先移除旧的再添加新的

### 8.3 被动免疫类

在 `LivingHurtEvent` / `LivingDamageEvent` 里判断：

```
如果 受击者是玩家 且 玩家有"火焰免疫"记忆 且 伤害源是火焰/岩浆：
    取消伤害 或 按比例减免
```

> **注意**：要覆盖的伤害源不止 `inFire`，还有岩浆、火焰弹、火焰附加、爆炸（部分）等。建议列一张**伤害类型白名单**。

### 8.4 爬墙与传送（难点）

| 能力 | 实现思路 |
|---|---|
| **爬墙** | 在 `PlayerTickEvent` 里检测玩家是否贴着可攀爬方块；若是，则给予一个向上的速度分量。参考原版蜘蛛的攀爬逻辑 |
| **短距传送** | 用 `RaycastBuilder` 找落点，然后 `teleportTo(...)`；需要处理"落点不可站立"的降级（向上找安全位置） |

## 九、网络同步

### 9.1 需要同步的数据

| 数据 | 方向 | 时机 |
|---|---|---|
| 忆格内容 | S2C | 写入 / 释放 / 腐坏 / 死亡清空 |
| 忆格上限（套装变化） | S2C | 装备变化时 |
| 认知过载层数 | 由状态效果自动同步 | — |
| 遗忘 / 失忆状态 | 由状态效果自动同步 | — |

### 9.2 实现方式

用 Forge 的 `SimpleChannel`：

```
① 在 FMLCommonSetupEvent + enqueueWork 里注册通道
② 每个包实现 encode / decode / handle
③ handle 里注意切主线程（用 context.enqueueWork）
④ 只发送变化，不要每 tick 发
```

> **踩坑**：`PlayerTickEvent` 里如果每次都发包，网络会被打爆。务必做**脏标记（dirty flag）**——只有忆格内容真的变了才发。
