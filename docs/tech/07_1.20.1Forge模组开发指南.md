## 一、环境准备（按顺序执行）

### 1.1 必需软件

| 软件 | 版本 | 说明 |
|---|---|---|
| **JDK 17** | 17.x | ⭐ **必须是 17**。Forge 1.20.1 不支持 21+，也不支持 8 |
| **IntelliJ IDEA** | 2023.x+ | 社区版够用 |
| Gradle | 由 wrapper 提供 | **不要**自己装 Gradle |
| Git | 任意 | 可选但强烈建议 |

**本机实测的 JDK 路径**：`D:\JAVA_DEV\JDK`（`javap` 可用，说明是完整 JDK 而非 JRE）

验证：

```bash
java -version    # 应输出 17.x
```

### 1.2 ⭐ 内存配置

`gradle.properties` 实测：

```properties
org.gradle.jvmargs=-Xmx3G
org.gradle.daemon=false
```

**为什么 `daemon=false`**：ForgeGradle 的 daemon 在 Windows 上容易残留文件锁，导致下次构建报"文件被占用"。关掉更稳（代价是每次构建慢几秒）。

**为什么是 3G**：ForgeGradle 反混淆 + 编译很吃内存。**低于 2G 会 OOM**，高于 4G 在 16G 机器上容易和 IDE 抢内存。

### 2.1 ⭐ 坑 #1：`gradle.properties` 的编码

**现象**：中文注释变乱码，或者构建时报 `Invalid character`。

**原因**：Gradle **强制以 ISO-8859-1 读取 `gradle.properties`**，不是 UTF-8。

**规则**：
- `gradle.properties` 里**只放 ASCII**
- 中文的模组名/简介 → 写到 `mods.toml`（UTF-8 资源文件）
- jar 文件名 → 用 ASCII（见坑 #2）

### 2.2 ⭐ 坑 #2：jar 文件名必须 ASCII

**现象**：游戏启动时崩溃，日志里有 `Invalid filename` 或直接静默不加载。

**原因**：Forge 的模组加载器**要求 jar 文件名是 ASCII**。

**实测的正确做法**（`build.gradle` 里）：

```groovy
version = mod_version
group = mod_group_id
// Forge 模组加载器要求 jar 文件名必须是 ASCII（否则启动时崩溃），
// 中文的模组显示名放在 mods.toml 的 displayName 里即可。
base {
    archivesName = "mnemosyne"
}
```

**注意 `base { archivesName = ... }`** —— 不是老的 `archivesBaseName = ...`（Gradle 8 已废弃后者）。

### 3.1 ⭐ 关键点逐条说明

**① `compileOnly ... :api` + `runtimeOnly`（不带 `:api`）**

```groovy
compileOnly fg.deobf("io.redspace:irons_spellbooks:${irons_spells_version}:api")
runtimeOnly  fg.deobf("io.redspace:irons_spellbooks:${irons_spells_version}")
```

- **`:api` 分类器** → 只含 `io.redspace.ironsspellbooks.api.*` 包。**编译期可见**，所以你的代码能 `import io.redspace.ironsspellbooks.api.spells.AbstractSpell;`
- **不带分类器** → 完整模组。**只做 runtime**，不打进你的 jar（因为玩家已经装了 ISS）

**这是整个依赖配置里最重要的一行。** 它决定了你的代码能用哪些 ISS 类（见 `01_ISS官方API参考.md` 的包可见性速查表）。

**② `mappings channel: 'official'`**

实测用 **official**（Mojang 官方映射），不是 `parchment` 或 `snapshot`。

**为什么重要**：映射方式决定你代码里方法名长什么样。official 映射下：
- `player.getInventory()`（不是 `m_36042_()`，也不是 `func_71045_()`）
- 但**原版方法在反编译时会显示成 `m_xxxxx_` 混淆名** —— 见坑 #4

**③ `runtimeOnly` 的三个前置**

```groovy
runtimeOnly fg.deobf("software.bernie.geckolib:geckolib-forge-${geckolib_version}")
implementation fg.deobf("dev.kosmx.player-anim:player-animation-lib-forge:${player_animator_version}")
runtimeOnly fg.deobf("top.theillusivec4.caelus:caelus-forge:${caelus_version}")
```

**⭐ 坑 #3：漏了这三个 → 开发环境启动崩溃**

ISS 3.16.3 运行时**硬依赖** GeckoLib 和 player-animator（用于实体动画），Caelus 用于鞘翅飞行（部分法术用）。

**现象**：`runClient` 时崩溃，日志里是 `NoClassDefFoundError: software/bernie/geckolib/...` 或 `Missing or unsupported mandatory dependencies`。

**注意**：`player-animator` 用 `implementation`（不是 `runtimeOnly`），因为 GeckoLib 的动画类需要它参与编译期解析。

**④ `processResources` 的变量替换**

```groovy
processResources {
    inputs.properties replaceProperties
    filesMatching(resourceTargets) { expand replaceProperties }
    filesMatching('*.mixins.json') { expand replaceProperties }
}
```

这让 `mods.toml` 里的 `${mod_id}`、`${mod_version}` 等被自动替换。**如果你的 `mods.toml` 里写了 `${...}` 但没在 `replaceProperties` 里定义，构建会报错。**

**⑤ `copyToMinecraftMods` 任务**

实测的一个非常实用的自动化：

```bash
./gradlew build                                    # 构建 + 自动复制到 PCL2 的 mods 目录
./gradlew build -Ppcl2_mods_dir=D:/some/mods       # 覆盖目标目录
```

`tasks.named('build').configure { dependsOn copyToMinecraftMods }` 让 `build` 自动带上复制。

**⭐ 坑 #4 的更正（Phase 0 实测，2026-09-15）**

> 原文写的是「`build/libs/` 里会同时有混淆版和 `-reobf` 版，发布要取 `-reobf` 的那个」。
> **这是 FG5 时代的行为，对 ForgeGradle 6 不成立。** 实测结果：

| 事实 | 证据 |
|---|---|
| `build/libs/` 里**只有一个** jar | 参考项目 `build/libs/` 只有 `randomspellbench-1.0.4.jar`；本项目只有 `mnemosyne-0.1.0.jar` |
| 这**唯一**的 jar **已经是 reobf 过的** | `javap -c` 该 jar 里的类，对原版的调用是 SRG 名：`Component.m_237115_`、`Button.m_253074_`、`Font.m_92852_` |
| 没有 `-reobf` 后缀的文件 | 构建日志里 `> Task :reobfJar` 执行后 `build/libs/` 仍只有一个文件 |

**结论**：ForgeGradle 6 的 `reobfJar` 是**就地重混淆**，`build/libs/mnemosyne-<version>.jar` 就是**可直接发布的成品**。

```
build/libs/mnemosyne-0.1.0.jar    ← 唯一产物：已 reobf，开发测试 + 发布都用它 ⭐
```

因此 `copyToMinecraftMods` 把**同一个文件**复制到 PCL2 的 mods 目录，行为完全正确
（PCL2 是正式游戏实例，需要的就是 reobf 版）。
**开发环境（`runClient`）根本不读这个 jar** —— 它走 `build.gradle` 里
`mods { "${mod_id}" { source sourceSets.main } }` 直接加载编译输出目录。

**发布时不需要再找 `-reobf` 文件**，`build/libs/mnemosyne-<version>.jar` 直接发。

### 4.1 ⭐ 三个关键细节

**① `displayName` 用中文完全没问题**

实测 `displayName="随机法术测试台"` —— **UTF-8 资源文件里中文是安全的**。这跟 `gradle.properties` 的限制不同。

**② `description` 支持 Minecraft 格式化代码**

`§b`（青色）、`§l`（粗体）、`§7`（灰色）、`§a`（绿色）、`§e`（黄色）、`§6`（金色）都能用。实测的 description 用了大量这种写法，效果是在模组列表里显示彩色分段。

**③ `ordering="AFTER"` 必须写**

```toml
ordering="AFTER"
```

**⭐ 坑 #5：不写 `AFTER` → 注册表竞态**

ISS 的 `SchoolRegistry` 是一个**自定义注册表**（`irons_spellbooks:schools`）。如果你在 `FMLCommonSetupEvent` 里往它注册，而 ISS 还没完成自己的注册，就会**注册失败或静默丢失**。

`ordering="AFTER"` 保证 ISS 先加载。

**⚠️ 但仅靠 `AFTER` 还不够** —— 见坑 #6。

### 4.2 ⭐ 坑 #6：自定义注册表注册的时序

**现象**：学派注册了，但游戏里查不到；或者偶尔能查到、偶尔不能（不确定性失败）。

**根因**：`FMLCommonSetupEvent` 是**并行执行**的。直接在事件回调里往注册表写数据会有线程安全问题。

**实测的正确写法**：

```java
public MnemosyneMod() {
    IEventBus modBus = FMLJavaModLoadingContext.get().getModEventBus();

    // 1. 标准 DeferredRegister 注册（属性、物品、声音等）
    ModAttributes.ATTRIBUTES.register(modBus);
    ModItems.ITEMS.register(modBus);
    ModSounds.SOUNDS.register(modBus);

    // 2. 自定义注册表（学派、法术）必须在 enqueueWork 里
    modBus.addListener(MnemosyneMod::onCommonSetup);
}

private static void onCommonSetup(FMLCommonSetupEvent event) {
    // ⭐ 必须 enqueueWork：把注册推迟到主线程，避免并行注册的竞态
    event.enqueueWork(() -> {
        ModSchools.register();   // 往 SchoolRegistry 写
        ModSpells.register();    // 往 SpellRegistry 写
    });
}
```

**规律**：

| 注册目标 | 时机 | 方式 |
|---|---|---|
| `DeferredRegister`（Forge 标准注册表：物品/方块/属性/声音/实体） | 构造函数里 | `.register(modBus)` |
| `DeferredRegister` 的**内容**（`.register("name", ...)` 的调用） | 构造函数里 | 直接调用 |
| **ISS 自定义注册表**（`SchoolRegistry` / `SpellRegistry`） | `FMLCommonSetupEvent` | ⭐ **`event.enqueueWork(...)`** |

**`SchoolRegistry` 和 `SpellRegistry` 都是自定义注册表，不是 Forge 标准注册表**，所以不能用 `DeferredRegister`。这一点见 `02_学派与属性注册.md`。

```java
import net.minecraftforge.fml.config.ModConfig;
import net.minecraftforge.fml.event.lifecycle.FMLCommonSetupEvent;
import net.minecraftforge.fml.javafmlmod.FMLJavaModLoadingContext;
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

@Mod(MnemosyneMod.MODID)
public class MnemosyneMod {
    public static final String MODID = "mnemosyne";
    public static final Logger LOGGER = LogManager.getLogger(MODID);

    public MnemosyneMod() {
        IEventBus modBus = FMLJavaModLoadingContext.get().getModEventBus();
        IEventBus forgeBus = MinecraftForge.EVENT_BUS;

        // 注册配置文件
        ModLoadingContext.get().registerConfig(ModConfig.Type.SERVER, Config.SERVER_SPEC);
        ModLoadingContext.get().registerConfig(ModConfig.Type.CLIENT, Config.CLIENT_SPEC);

        // ---- Forge 标准注册表 ----
        ModAttributes.ATTRIBUTES.register(modBus);
        ModItems.ITEMS.register(modBus);
        ModSounds.SOUNDS.register(modBus);

        // ---- 自定义注册表（延迟到主线程）----
        modBus.addListener(MnemosyneMod::onCommonSetup);

        // ---- Forge 事件总线 ----
        // 注意：带 @Mod.EventBusSubscriber 的类会自动注册，勿重复注册。
        // 只有需要手动注册的类才写在这里。
    }

    private static void onCommonSetup(FMLCommonSetupEvent event) {
        event.enqueueWork(() -> {
            ModSchools.register();
            ModSpells.register();
        });
    }
}
```

### 5.1 ⭐ 双事件总线 —— 必须搞清楚

| 总线 | 获取方式 | 什么时候触发 | 放什么 |
|---|---|---|---|
| **MOD 总线** | `FMLJavaModLoadingContext.get().getModEventBus()` | 模组**加载期**（注册、初始化） | 注册表注册、`FMLCommonSetupEvent`、`FMLClientSetupEvent`、`RegisterClientReloadListenersEvent` |
| **FORGE 总线** | `MinecraftForge.EVENT_BUS` | **游戏运行期**（每 tick、玩家事件） | `PlayerTickEvent`、`SpellOnCastEvent`、`LivingDamageEvent` |

**⭐ 坑 #7：注册到错误的总线 → 事件永远不触发**

**规律**：
- 事件类名以 `FML` 开头，或叫 `Register*` / `*SetupEvent` → **MOD 总线**
- 事件类名是 `PlayerEvent` / `LivingEvent` / `TickEvent` / ISS 的 `Spell*Event` → **FORGE 总线**

**最省事的做法**：用注解自动注册，不手动 `register`。

```java
// 注册到 MOD 总线
@Mod.EventBusSubscriber(modid = MnemosyneMod.MODID, bus = Mod.EventBusSubscriber.Bus.MOD)
public final class ModSetupEvents {
    @SubscribeEvent
    public static void onClientSetup(FMLClientSetupEvent event) { }
}

// 注册到 FORGE 总线
@Mod.EventBusSubscriber(modid = MnemosyneMod.MODID, bus = Mod.EventBusSubscriber.Bus.FORGE)
public final class MnemosyneEvents {
    @SubscribeEvent
    public static void onSpellCast(SpellOnCastEvent event) { }
}
```

**⚠️ 用了注解就不要再 `bus.register()`** —— 会注册两次，事件触发两次。实测项目的注释里专门写了这句：

> `// 注意：ModEvents 已通过 @Mod.EventBusSubscriber 自动注册，勿重复注册。`

## 六、包可见性与反射

### 6.1 ⭐ 坑 #8：ISS 的 API 边界

**这是做 ISS 附属模组最反直觉的一点。**

`compileOnly ... :api` 只给了你 `io.redspace.ironsspellbooks.api.*`。**其它所有包编译期都不可见。**

| 包 | 编译期可见？ | 内容 |
|---|---|---|
| `io.redspace.ironsspellbooks.api.*` | ✅ | `AbstractSpell`、`SchoolType`、`SpellData`、`ISpellContainer`、`SpellRegistry`、`SchoolRegistry`、`MagicData`、所有 `api.events.*` |
| `io.redspace.ironsspellbooks.item.*` | ❌ | `Scroll`、`SpellBook`、`UniqueSpellBook` |
| `io.redspace.ironsspellbooks.capabilities.*` | ❌ | `SyncedSpellData` |
| `io.redspace.ironsspellbooks.spells.*` | ❌ | 所有官方法术实现 |
| `io.redspace.ironsspellbooks.entity.*` | ❌ | 所有实体 |
| `io.redspace.ironsspellbooks.block.*` | ❌ | 所有方块 |

### 6.2 ⭐ `MagicData` 是个特例 —— 类可见，但返回值不可见

`MagicData` 本身在 **api 包**（`io.redspace.ironsspellbooks.api.magic.MagicData`）✅ 可 `import`。

但它有一个方法：

```java
public static MagicData getPlayerMagicData(Player player);   // ✅ 返回类型可见
public SyncedSpellData getSyncedData();                       // ❌ SyncedSpellData 在 capabilities 包
```

**结果**：你能拿到 `MagicData`，但**不能声明 `SyncedSpellData` 类型的变量**。

**实测的解决方案（反射 + 缓存）**：

```java
public final class SpellLearnHelper {
    private static volatile Method cachedLearnSpell;
    private static volatile Method cachedGetSyncedData;
    private static final AtomicBoolean loggedFailure = new AtomicBoolean(false);

    public static boolean learn(ServerPlayer player, AbstractSpell spell) {
        if (player == null || spell == null) return false;
        try {
            Object magicData = MagicData.getPlayerMagicData(player);
            if (magicData == null) return false;

            Object syncedData = invoke(cachedGetSyncedData, magicData);
            if (syncedData == null) return false;

            Method method = cachedLearnSpell;
            if (method == null) {
                // ⭐ 多签名回退：ISS 不同版本方法签名可能不同
                try {
                    method = syncedData.getClass().getMethod("learnSpell", AbstractSpell.class);
                } catch (NoSuchMethodException e) {
                    method = syncedData.getClass().getMethod("learnSpell", AbstractSpell.class, boolean.class);
                }
                cachedLearnSpell = method;
            }
            if (method.getParameterCount() == 2) {
                method.invoke(syncedData, spell, false);
            } else {
                method.invoke(syncedData, spell);
            }
            return true;
        } catch (Throwable t) {
            // ⭐ 首次 warn，之后 debug：避免 ISS 不兼容时日志刷屏
            if (loggedFailure.compareAndSet(false, true)) {
                LOG.warn("Failed to learn spell {} for {}: {}",
                        spell.getSpellId(), player.getName().getString(), t.toString());
            } else {
                LOG.debug("Failed to learn spell {} for {}: {}",
                        spell.getSpellId(), player.getName().getString(), t.toString());
            }
            return false;
        }
    }
}
```

**⭐ 这个模式的四个要点（务必照抄）**：

| 要点 | 为什么 |
|---|---|
| **`Method` 静态缓存** | 反射的 `getMethod` 很慢，每次调用都查会明显卡顿 |
| **多签名回退** | ISS 小版本更新可能改签名。先试单参，失败再试双参 |
| **`AtomicBoolean` 只 warn 一次** | 否则玩家每次操作都刷日志，几秒钟几 MB |
| **`catch (Throwable)`** | 不只是 `Exception`。反射可能抛 `LinkageError` |

**🔑 更重要的结论**：**能不用反射就不用反射。**

对于忆海：
- 卷轴 → ✅ 用 `ISpellContainer`（api 包），**零反射**
- 法术书读取 → ✅ 用 `ISpellContainer`，**零反射**
- 学习法术 → ❌ 需要反射（`SyncedSpellData.learnSpell`）
- 读取玩家已学法术 → ❌ 需要反射

**所以忆海的核心功能（忆格、共鸣、遗忘）尽量设计成基于 `ISpellContainer` + 你自己的 `getPersistentData()`，而不是依赖 ISS 的玩家法术列表。** 这样能避开 90% 的反射风险。

### 7.3 网络包（服务端权威）

实测项目的架构：

```
客户端                         服务端
   │                              │
   │  C2SUpdateSpellFilterPacket  │
   │ ────────────────────────────>│
   │                              │ 校验权限 + 执行业务逻辑
   │  S2CSyncConfigPacket         │
   │ <────────────────────────────│
   │                              │
   ▼ 更新本地 UI                   ▼ 权威数据源
```

**实测的 `NetworkHandler` 骨架**：

```java
public final class NetworkHandler {
    public static final String PROTOCOL_VERSION = "1.0";

    public static final SimpleChannel CHANNEL = NetworkRegistry.newSimpleChannel(
            ResourceLocation.fromNamespaceAndPath(MnemosyneMod.MODID, "main"),
            () -> PROTOCOL_VERSION,
            PROTOCOL_VERSION::equals,
            PROTOCOL_VERSION::equals
    );

    public static void register() {
        int id = 0;
        register(++id, C2SUpdateEngramPacket.class,
                C2SUpdateEngramPacket::encode, C2SUpdateEngramPacket::decode, C2SUpdateEngramPacket::handle,
                NetworkDirection.PLAY_TO_SERVER);
        // ...
    }

    private static <T> void register(int id, Class<T> clazz,
            BiConsumer<T, FriendlyByteBuf> encoder,
            Function<FriendlyByteBuf, T> decoder,
            BiConsumer<T, Supplier<NetworkEvent.Context>> consumer,
            NetworkDirection direction) {
        CHANNEL.registerMessage(id, clazz, encoder, decoder, consumer, Optional.of(direction));
    }
}
```

**⭐ 三个必须遵守的规则**：

1. **`NetworkHandler.register()` 必须在 `event.enqueueWork(...)` 里调用**（见坑 #6，网络通道必须在主线程初始化）
2. **`ResourceLocation.fromNamespaceAndPath(...)`** 是 1.20.1 的正确写法，不是 `new ResourceLocation(...)`
3. **消息 ID 必须唯一且从 0 开始连续**（用 `++id` 自增最安全）

**⭐ 坑：ID 重复 → 连接被踢**

如果两个包用了同一个 ID，玩家进服务器时会被踢出，日志是 `Payload may not be larger than ...` 或 `Unknown packet id`。**加包时务必用 `++id`。**

## 十、九个坑速查表

| # | 坑 | 症状 | 解决 |
|---|---|---|---|
| 1 | `gradle.properties` 是 ISO-8859-1 | 中文乱码 / 构建报错 | 只放 ASCII，中文写 `mods.toml` |

| 5 | 依赖没写 `ordering="AFTER"` | 注册表竞态，学派丢失 | `mods.toml` 里写 `ordering="AFTER"` |
| 6 | 自定义注册表在 `FMLCommonSetupEvent` 直接注册 | 不确定性失败 | ⭐ `event.enqueueWork(...)` |
| 7 | 事件注册到错误的总线 | 事件永不触发 | FML/Register/Setup → MOD 总线；其余 → FORGE 总线 |
| 8 | 反射无缓存 / 无日志限流 | 卡顿 + 日志刷屏 | 缓存 `Method` + `AtomicBoolean` 只 warn 一次 |
| **9** | ⭐ **前置版本按"老攻略"抄** | `runClient` 直接崩：`Missing or unsupported mandatory dependencies` | 见下方 |

### ⭐ 坑 #9：前置版本必须去问 ISS，不能抄老攻略（Phase 0 实测）

**症状**（`./gradlew runClient` 的输出，逐字）：

```
[main/ERROR] [ne.mi.fm.lo.ModSorter/LOADING]: Missing or unsupported mandatory dependencies:
	Mod ID: 'curios', Requested by: 'irons_spellbooks', Expected range: '[5.14.1+1.20.1,)', Actual version: '5.4.7+1.20.1'
	Mod ID: 'irons_lib', Requested by: 'irons_spellbooks', Expected range: '[1.20.1-2,1.20.1-3)', Actual version: '[MISSING]'
...
[Render thread/FATAL]: Crash report saved to .\crash-reports\crash-2025-...-fml.txt
java.lang.Exception: Mod Loading has failed
```

**两个根因**：

| 根因 | 说明 |
|---|---|
| **Curios 版本太老** | 网上大量 ISS 附属教程写的是 `curios 5.4.7+1.20.1`（那是 ISS 3.4.x 时代的要求）。ISS 3.16.3 已经把下限抬到 **`5.14.1+1.20.1`**。 |
| **少了 `irons_lib`** | ISS 1.20.1-3.16.3 引入了独立的库前置 `irons_lib`，范围 `[1.20.1-2,1.20.1-3)`。**ISS 的 POM 里没有任何 `<dependencies>`**（实测：整份 POM 只有 groupId/artifactId/version），所以 Gradle **不会**自动带进来，必须手动声明。 |

**为什么构建期完全看不出来**：`./gradlew build` 会 **`BUILD SUCCESSFUL`**，
因为这两个依赖只影响**运行时**的 `ModSorter`。**只有真正启动游戏才会暴露。**

**修法**（`gradle.properties` + `build.gradle`）：

```properties
curios_version=5.14.1+1.20.1
irons_lib_version=1.20.1-2.1.0
```

```groovy
runtimeOnly fg.deobf("io.redspace:irons_lib:${irons_lib_version}")
```

**验证版本下限的权威方法**（不要信攻略，信 jar）：

```bash
# 直接从 ISS 的 jar 里读它自己声明的依赖范围
unzip -p irons_spellbooks-1.20.1-3.16.3.jar META-INF/mods.toml | grep -A4 dependencies
```

**顺带一个教训**：`D:\桌面\1.20.1forge模组开发`（参考项目）的 `gradle.properties` 里
同样写着 `curios 5.4.7` 且没有 `irons_lib` —— 它能 `build` 成功、能发布，
但**它的 `runClient` 从来没能进过主菜单**。抄配置时不要把"能 build"当成"能跑"。

### 额外提醒：三条非阻塞的编译警告（Phase 0 实测）

在 Forge 47.4.0 下用 §5 的主类写法，`compileJava` 会报 3 条 `[removal]` 警告：

```
MnemosyneMod.java:38: 警告: [removal] FMLJavaModLoadingContext 中的 get() 已过时, 且标记为待删除
MnemosyneMod.java:44: 警告: [removal] ModLoadingContext 中的 get() 已过时, 且标记为待删除
MnemosyneMod.java:45: 警告: [removal] ModLoadingContext 中的 get() 已过时, 且标记为待删除
```

**它们只是警告，`BUILD SUCCESSFUL` 不受影响。** 要消除可以用 Forge 47 的构造器注入写法：

### 额外提醒：`ResourceLocation` 的构造

1.20.1 的**正确写法**：

```java
ResourceLocation.fromNamespaceAndPath("mnemosyne", "memory_arrow")   // ✅
ResourceLocation.parse("mnemosyne:memory_arrow")                     // ✅
new ResourceLocation("mnemosyne", "memory_arrow")                    // ⚠️ 已废弃但能用
new ResourceLocation("mnemosyne:memory_arrow")                       // ⚠️ 已废弃但能用
```

实测项目用的是 `ResourceLocation.fromNamespaceAndPath(...)`。**用新写法，避免未来升级报废弃警告。**
