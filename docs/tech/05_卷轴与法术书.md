# 05 · 卷轴与法术书 API

> 本文件是 `mnemosyne`（忆海 / 记忆·认知流派）技术文档集的第 5 篇。
> 所有结论均来自对 `irons_spellbooks-1.20.1-3.16.3` 反编译（javap + 常量池解析）的**实测结果**，不是推测。
> 标注 `✅ 可直接调用` 的 API 位于 `io.redspace.ironsspellbooks.api.*`，第三方模组**编译期可见**，无需反射。
> 标注 `⚠️ 需反射` 的 API 位于非 api 包，编译期不可见。

---

## 〇、一句话结论（先看这个）

**卷轴和法术书的整个数据层都由 `ISpellContainer` 这一个接口驱动，而 `ISpellContainer` 位于 `api` 包内，静态工厂方法是 `public static` 的。**

这意味着：

- ✅ 你的模组**可以完全用官方 API 创建、读写、修改卷轴和法术书**，不需要反射、不需要 Mixin、不需要自己实现 NBT 格式。
- ✅ 你的自定义卷轴只要 `implements IScroll`（空标记接口），就会被官方的卷轴识别逻辑接受。
- ⚠️ 只有 `Scroll` 和 `SpellBook` 这两个**具体物品类**在非 api 包，无法直接 `extends`；但你可以复制它们的实现思路，或者直接注册**官方卷轴物品的多个变体**。

这是整个项目里最省事的一块。

## 一、卷轴系统的真实结构

### 1.1 类关系（实测）

```
net.minecraft.world.item.Item
  └── io.redspace.ironsspellbooks.item.Scroll        ⚠️ 非 api 包
        implements io.redspace.ironsspellbooks.api.item.IScroll   ✅ 空标记接口
```

```java
// javap 实测输出
public interface io.redspace.ironsspellbooks.api.item.IScroll {
    // 空接口，没有任何方法
}
```

**关键洞察**：`IScroll` 是**纯标记接口**（marker interface）。官方代码在判断"这个物品是不是卷轴"时用的是 `instanceof IScroll`。所以：

```java
// 你自己的卷轴类，放在你的包里，完全可以编译通过
public class MemoryScrollItem extends Item implements IScroll {
    public MemoryScrollItem(Properties props) { super(props); }
}
```

只要 `implements IScroll`，官方的以下逻辑就会认它：
- 卷轴合成台的输入槽校验
- 卷轴袋（Scroll Pouch）的收纳
- 商人交易池
- 战利品生成函数 `randomize_spell`
- 提示框的卷轴专属渲染

### 1.2 `Scroll` 类的完整方法清单（实测）

```
public class io.redspace.ironsspellbooks.item.Scroll extends Item implements IScroll
  public Scroll(Item$Properties)
  private SpellData getSpellSlotFromStack(ItemStack)              // 私有，读卷轴里的法术
  protected void removeScrollAfterCast(ServerPlayer, ItemStack)   // 施法后销毁卷轴
  public static void attemptRemoveScrollAfterCast(ServerPlayer)   // ✅ 静态，可调用
  public String getCreatorModId(ItemStack)                        // ⭐ 决定 tooltip 显示哪个模组
  public InteractionResultHolder<ItemStack> use(Level, Player, InteractionHand)
  public Component getName(ItemStack)
  public void appendHoverText(ItemStack, Level, List<Component>, TooltipFlag)
```

### 1.3 ⭐ `getCreatorModId` —— 最容易踩的坑

```java
public String getCreatorModId(ItemStack stack)
```

这个方法返回的字符串**决定物品 tooltip 里那行灰色的"模组名"显示什么**。

- 官方 `Scroll` 的返回值是**动态**的：它读取卷轴里 `SpellData` 对应的法术，然后返回**那个法术所属的模组 ID**。
- 这就是为什么"铁魔法的卷轴"在装了附属模组后会显示成附属模组的名字 —— 因为法术是附属模组注册的。

**对你的项目意味着什么**：

你的忆海卷轴如果直接用官方的 `irons_spellbooks:scroll` 物品（只是塞了你的法术），tooltip 会**自动**显示 `Mnemosyne`。你不需要做任何事。

如果你自己注册一个 `mnemosyne:memory_scroll` 物品，那么你**必须重写** `getCreatorModId`，否则会返回 `mnemosyne`（默认行为，其实也对），但如果你想让玩家看到"忆海"的中文名，需要返回你的 modid 并在 `mods.toml` 里配好 `displayName`。

**推荐做法**：**不要**新注册卷轴物品。直接复用 `irons_spellbooks:scroll`。理由见 §1.4。

### 1.4 推荐方案：复用官方卷轴物品

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 复用官方卷轴**（推荐） | 不注册新物品，用 `ISpellContainer.createScrollContainer(你的法术, 等级, stack)` 把法术塞进官方 `irons_spellbooks:scroll` | 零兼容问题；tooltip 自动正确；合成台/卷轴袋/商人全部自动支持 | 视觉上和别的学派卷轴一样（只有法术名不同） |
| **B. 自注册卷轴** | 注册 `mnemosyne:memory_scroll extends Item implements IScroll` | 可以有自己的模型/贴图/粒子 | 要自己重写 `use()`、`getName()`、`appendHoverText()`；要自己处理"施法后销毁"；容易被其他模组的硬编码判断漏掉 |

**结论：M1～M4 阶段用方案 A，M7 之后如果美术资源到位再考虑 B。**

方案 A 的完整代码路径：

```java
// 创建一个 3 级的「忆矢」卷轴
ItemStack scroll = new ItemStack(irons_spellbooks.scroll); // 官方卷轴物品
ISpellContainer.createScrollContainer(
        SpellRegistry.getSpell(ResourceLocation.parse("mnemosyne:memory_arrow")), // 法术
        3,                                                                        // 等级
        scroll                                                                    // 目标 ItemStack
);
// 内部已自动调用 save()，直接给玩家即可
player.addItem(scroll);
```

`createScrollContainer` 是 `public static`，**这是本文件最重要的一个 API**。

### 1.5 卷轴消耗逻辑（实测）

卷轴是**一次性**的：

```
玩家用卷轴施法
  → Scroll.use() 被调用
  → 校验玩家是否真的施放成功（返回 CastResult）
  → 成功则调用 removeScrollAfterCast()
  → 官方用 static 的 attemptRemoveScrollAfterCast(ServerPlayer) 统一处理
  → 卷轴数量 -1（创造模式除外）
```

**注意**：官方是**施法成功后**才销毁卷轴，不是"右键就销毁"。如果你的忆海法术有"施法失败返还"的机制，这个逻辑天然兼容。

## 二、`SpellData` —— 法术数据的原子单位

### 2.1 完整结构（实测）

```java
public class io.redspace.ironsspellbooks.api.spells.SpellData
        implements Comparable<SpellData> {

    // ---- NBT 常量（实测字符串值）----
    public static final String SPELL_ID;      // "id"
    public static final String SPELL_LEVEL;   // "level"
    public static final String SPELL_LOCKED;  // "locked"

    public static final Codec<SpellData> CODEC;
    public static final SpellData EMPTY;

    protected final AbstractSpell spell;
    protected final int spellLevel;
    protected final boolean locked;

    // ---- 构造函数 ----
    public SpellData(AbstractSpell spell, int level, boolean locked);
    public SpellData(AbstractSpell spell, int level);          // locked = false
    public SpellData(ResourceLocation spellId, int level, boolean locked);

    // ---- 序列化 ----
    public static void writeToBuffer(FriendlyByteBuf, SpellData);
    public static SpellData readFromBuffer(FriendlyByteBuf);

    // ---- 访问器 ----
    public AbstractSpell getSpell();
    public int getLevel();
    public boolean isLocked();
    public boolean canRemove();     // ⭐ 判断这个法术能不能被玩家移除
    public SpellRarity getRarity(); // ⭐ 根据等级反推稀有度（见 04 号文档）
    public Component getDisplayName();
}
```

### 2.2 三个字段的语义

| 字段 | NBT 键 | 类型 | 含义 |
|---|---|---|---|
| `spell` | `id` | `ResourceLocation` | 法术 ID，如 `mnemosyne:memory_arrow` |
| `spellLevel` | `level` | `int` | 法术等级 1~`maxLevel` |
| `locked` | `locked` | `boolean` | 锁定后玩家**不能主动遗忘/替换**这个法术 |

### 2.3 ⭐ `locked` 字段对忆海的意义

`locked` 是官方为"不可移除法术"设计的（例如某些法术书的初始法术）。

**忆海的天然用法**：`02_核心机制_遗忘与能力映射.md` 里的「痛忆」——玩家从怪物身上掠夺来的记忆。

建议规则：
- **术忆**（自己学会的）→ `locked = false`，可自由遗忘
- **质忆**（装备/记忆碑获得的）→ `locked = false`
- **痛忆**（从怪物掠夺的）→ `locked = true`，**必须经过"遗忘仪式"才能移除**，不能直接丢弃

这样"掠夺来的能力带着原主人的印记，需要付出代价才能抹去"就有了机制层面的落地，而不只是文案。

### 2.4 `canRemove()` 的行为

```java
public boolean canRemove();
```

实测逻辑：返回 `!locked`（并且该法术允许被移除）。**这是官方给的公开接口**，所以你的"遗忘仪式"逻辑里应该直接调用它，而不是自己判断 `locked`：

```java
if (!spellData.canRemove()) {
    // 提示玩家：这是掠夺来的痛忆，需要先进行遗忘仪式
    player.displayClientMessage(Component.translatable("mnemosyne.msg.locked_memory"), true);
    return;
}
```

## 三、`ISpellContainer` —— 法术容器（核心）

### 3.1 为什么它这么重要

`ISpellContainer` 是**卷轴和法术书共用的数据抽象**。一个 `ItemStack` 只要有 `ISpellContainer`，它就"能装法术"。

- 卷轴 = 只装 1 个法术、用后即毁的容器
- 法术书 = 装 N 个法术、`mustEquip=true` 的容器
- 你的忆碑物品 = 可以是一个装 1 个法术、**永久保留**的容器

### 3.2 NBT 结构（实测常量）

```java
public static final String NBT        = "irons_spellbooks:spell_container";
public static final String LEGACY_NBT = "ISB_Spells";
```

⚠️ **不要自己手写这个 NBT**。官方有 `CodecHelper.getOrElseWithLegacy` 的向后兼容读取，手写格式在版本更新时必炸。

### 3.3 完整方法清单（实测）

```java
public interface io.redspace.ironsspellbooks.api.spells.ISpellContainer {

    // ================= 静态工厂（✅ 全部 public static，可直接调用）=================
    static boolean isSpellContainer(ItemStack);
    static ISpellContainer create(int maxSpellCount, boolean mustEquip, boolean isSpellWheel);
    static ISpellContainer createScrollContainer(AbstractSpell spell, int level, ItemStack stack);
    static ISpellContainer createImbuedContainer(AbstractSpell spell, int level, ItemStack stack);
    static ISpellContainer get(ItemStack);
    static ISpellContainer getOrCreate(ItemStack);
    static void set(ItemStack, ISpellContainer);
    static void remove(ItemStack);

    // ================= 实例方法 =================
    SpellSlot[] getAllSpells();
    List<SpellSlot> getActiveSpells();
    int getMaxSpellCount();
    int getActiveSpellCount();
    int getNextAvailableIndex();
    boolean mustEquip();
    boolean isImproved();
    boolean isSpellWheel();
    SpellData getSpellAtIndex(int index);
    int getIndexForSpell(AbstractSpell spell);
    boolean isEmpty();
    ISpellContainerMutable mutableCopy();     // ⭐ 拿到可变副本才能改
    boolean addSpell(AbstractSpell spell, int level, boolean locked, ItemStack stack);
    void save(ItemStack stack);               // ⭐ 改完必须 save
}
```

### 3.4 ⭐ 可变 vs 不可变 —— 最关键的编程范式

`ISpellContainer` 本身是**只读**的。要修改必须走这条路：

```
ISpellContainer.get(stack)          →  只读视图
        ↓ .mutableCopy()
ISpellContainerMutable              →  可改
        ↓ addSpell / removeSpell / setMaxSpellCount ...
ISpellContainerMutable.toImmutable()
        ↓
ISpellContainer.set(stack, ...)  或  .save(stack)
```

```java
// javap 实测
public interface io.redspace.ironsspellbooks.api.spells.ISpellContainerMutable {
    void setMaxSpellCount(int);
    void setImproved(boolean);
    boolean addSpellAtIndex(AbstractSpell, int level, int index, boolean locked);
    boolean addSpell(AbstractSpell, int level, boolean locked);
    boolean removeSpellAtIndex(int);
    boolean removeSpell(AbstractSpell);
    SpellSlot[] getAllSpells();
    List<SpellSlot> getActiveSpells();
    int getMaxSpellCount();
    int getActiveSpellCount();
    int getNextAvailableIndex();
    boolean mustEquip();
    boolean isImproved();
    boolean isSpellWheel();
    SpellData getSpellAtIndex(int);
    int getIndexForSpell(AbstractSpell);
    boolean isEmpty();
    ISpellContainer toImmutable();
}
```

**标准改写模式**（务必背下来）：

```java
public static void addSpellToStack(ItemStack stack, AbstractSpell spell, int level, boolean locked) {
    ISpellContainer container = ISpellContainer.get(stack);
    if (container == null) {
        container = ISpellContainer.create(1, false, false);
    }
    ISpellContainerMutable mutable = container.mutableCopy();
    mutable.addSpell(spell, level, locked);
    ISpellContainer.set(stack, mutable.toImmutable());
}
```

### 3.5 三种容器工厂的区别

| 工厂方法 | 用途 | 行为差异 |
|---|---|---|
| `create(maxCount, mustEquip, isSpellWheel)` | 通用容器 | 最底层，参数自己定 |
| `createScrollContainer(spell, level, stack)` | **卷轴** | 单法术槽；`mustEquip=false`；自动 `save()` 到 stack |
| `createImbuedContainer(spell, level, stack)` | **灌注装备** | 用于"把法术灌注到武器/护甲"的场景 |

**忆海的用法**：
- 忆海卷轴 → `createScrollContainer`
- 忆碑物品 → `create(1, false, false)` + `addSpell(..., locked=true)`
- **质忆装备**（07 号文档里的"铭刻护甲"）→ `createImbuedContainer`

### 3.6 `SpellSlot`（record）

```java
public final class io.redspace.ironsspellbooks.api.spells.SpellSlot extends Record {
    SpellData spellData();
    int index();
    AbstractSpell getSpell();
    int getLevel();
    boolean isLocked();
    static SpellSlot of(SpellData, int);
}
```

遍历法术书内容的正确姿势：

```java
ISpellContainer container = ISpellContainer.get(stack);
for (SpellSlot slot : container.getActiveSpells()) {
    SpellData data = slot.spellData();
    int index = slot.index();
    // ...
}
```

`getActiveSpells()` 会**跳过空槽**，`getAllSpells()` 返回定长数组（含空槽 `SpellData.EMPTY`）。

### 4.3 ⭐ 法术书等级 = `maxSpellSlots` + 属性

**ISS 里"法术书等级"不是一个独立概念**，它由两个东西共同表达：

1. **`maxSpellSlots`（法术槽数量）** —— 决定能装几个法术
2. **`withAttribute(属性, 数值)`** —— 决定各学派的法术强度/抗性加成

官方法术书的梯度（实测自 `SimpleAttributeSpellBook` 的注册调用）：

| 法术书 | 槽位 | 属性加成特点 |
|---|---|---|
| 学徒法书 Apprentice | 3~4 | 单学派 +10% 左右 |
| 法师法书 Mage | 5~6 | 单学派 +15%~20% |
| 大法师法书 Archmage | 8 | 多学派 +10% |
| 独特法书（如血书/死灵书） | 5~6 | 特殊机制 + 强属性 |

### 4.4 ⭐ 对忆海的落地建议：忆海法书的 5 个等级

> ⚠️ **【已作废 · 2026-09-18】本节描述的 5 级忆海法书（残忆 / 铭忆 / 溯忆 / 沧忆 / 忆海法典）
> 已从模组中全部删除。** 理由：与 ISS 官方的学徒 / 法师 / 大法师法书功能完全重叠，
> 属于多余设计。忆海现在**复用 ISS 官方法术书**，本学派只提供忆者法袍作为属性来源。
> 下方的等级表、槽位、属性加成、解锁条件**均不再适用于本模组**，保留仅为记录设计推演过程。
> 对应的 `mnemosyne:spell_book_t1..t5` 物品、配方、战利品条目、语言键、模型与贴图都已移除。

严格对标官方的"等级感"，但用忆海的机制语言重新表达：

| 等级 | 中文名 | 槽位 | 属性加成 | 忆格加成 | 解锁条件 |
|---|---|---|---|---|---|
| T1 | **残忆法书** | 3 | 记忆法术强度 +5% | 无 | 合成：忆晶 ×4 + 书 |
| T2 | **铭忆法书** | 5 | 记忆法术强度 +10%、记忆抗性 +5% | 忆格 +1 | 忆者遗迹宝箱 |
| T3 | **溯忆法书** | 6 | 记忆法术强度 +15%、记忆抗性 +10% | 忆格 +1 | 记忆碑解锁 |
| T4 | **沧忆法书** | 8 | 记忆法术强度 +20%、记忆抗性 +15% | 忆格 +1 | 击败「守忆者」掉落 |
| T5 | **忆海法典**（独特） | 8 | 记忆法术强度 +30%、记忆抗性 +25% | 忆格 +2 | 三块记忆碑碎片合成 |

**注意与 01 号文档的一致性**：忆格基础 3 格、上限 5 格。上表的"忆格 +1/+2"是**装备加成**，需要和 07 号文档的铭刻护甲套装加成统一计算，**总上限不得超过 5**。

推荐实现方式：忆格加成不要用 `withAttribute`（那是法术强度的机制），而是**在你的忆格管理器里读取玩家当前装备的法书 + 护甲，累加后 clamp 到 5**。

## 五、铭刻台（Inscription Table）与卷轴合成台

### 5.1 铭刻台 InscriptionTableBlock

```
io.redspace.ironsspellbooks.block.inscription_table.InscriptionTableBlock   ⚠️ 非 api
```

**功能**：把卷轴上的法术**永久抄录**到法术书里（消耗卷轴）。

**相关 lang 键（实测）**：

```json
"ui.irons_spellbooks.inscription_table_rarity_error": "This scroll is too rare for this spell book."
```

**⚠️ 重要机制：稀有度门槛**

铭刻台会拒绝"稀有度高于法术书承受上限"的卷轴。这就是 `SpellRarity` 在游戏性上的实际作用点之一。

**对忆海的影响**：忆海有 2 个 Legendary 法术。如果玩家拿 T1 残忆法书去铭刻千忆归一卷轴，会被拒。这是**好的设计**——它天然形成了"高阶法术需要高阶法书"的进度墙，和忆海的"记忆需要承载力"设定完全吻合。

**建议**：不要绕过这个限制，而是**把这条错误提示本地化并改写成忆海语境**：

```json
"ui.irons_spellbooks.inscription_table_rarity_error": "这本书承载不了如此沉重的记忆。"
```

**对忆海的落地**：

`InkItem` 在非 api 包 ⚠️。但你**不需要**注册新的墨水瓶物品。两种做法：

**做法 A（推荐）**：让忆海卷轴由**官方墨水瓶 + 忆晶**在官方卷轴合成台里产出。这需要往官方合成台注入"忆海学派"的配方。官方合成台读取的是 `InkItem` 的学派字段，**你无法直接改**。

**做法 B（更稳）**：注册你自己的 **忆海铭刻台 `mnemosyne:memory_loom`**，输入 `忆晶 + 纸 + 空卷轴`，输出随机忆海法术卷轴。完全自实现，不受官方实现约束。

**做法 C（最省事，M1 阶段用）**：忆海卷轴**只从忆者遗迹的宝箱里产出**（用 §6 的战利品函数），不做合成台。等 M6 美术资源到位再补做法 B。

### 5.3 战利品函数 `randomize_spell`（✅ 官方已注册，JSON 里可直接用）

实测类：

```java
public class io.redspace.ironsspellbooks.loot.RandomizeSpellFunction
        extends LootItemConditionalFunction {

    final NumberProvider qualityRange;
    final SpellFilter applicableSpells;

    protected ItemStack run(ItemStack, LootContext);
    private NavigableMap<Integer, AbstractSpell> getWeightedSpellList(List<AbstractSpell>);
    private int getWeightFromRarity(SpellRarity);
    public <N extends NumberProvider> N getQualityRange();
}
```

**JSON 用法（实测自 `worldgen/scroll_gen.json` 和遗迹宝箱）**：

```json
{
  "function": "irons_spellbooks:randomize_spell",
  "levels": { "min": 1, "max": 10 }
}
```

```json
{
  "function": "irons_spellbooks:randomize_spell",
  "quality": { "min": 0.6, "max": 1.0 },
  "spell_filter": { "school": "irons_spellbooks:fire" }
}
```

**三种参数**：

| 参数 | 类型 | 作用 |
|---|---|---|
| `levels` | `{min, max}` | 直接指定法术等级范围 |
| `quality` | `{min, max}` 0.0~1.0 | 品质区间，内部映射到等级/稀有度 |
| `spell_filter` | `{school: "..."}` | ⭐ **限定学派** |

**⭐ 关键结论**：`spell_filter` 支持按学派过滤。所以：

```json
{
  "function": "irons_spellbooks:randomize_spell",
  "quality": { "min": 0.0, "max": 0.5 },
  "spell_filter": { "school": "mnemosyne:memory" }
}
```

**忆者遗迹的宝箱会只产出忆海学派的卷轴**，官方函数自动处理权重（内部 `getWeightFromRarity` 按稀有度给权重）。你**零代码**实现。

⚠️ **验证点**：`SpellFilter` 的 `school` 字段实测接受 `ResourceLocation`。M1 阶段务必实测一次，确认第三方学派能被正确过滤（这是官方给第三方学派留的口子，理论上支持，但必须验证）。

## 六、忆海专属的容器设计

### 6.1 忆碑物品（Memory Stele Item）

`08_建筑_忆者遗迹.md` 里的"记忆碑"在结构里是一个方块。但玩家可以把它**搬回家**。

```java
// 忆碑物品 = 一个永久容器，装 1 个 locked 法术
ISpellContainer container = ISpellContainer.create(1, false, false);
ISpellContainerMutable mutable = container.mutableCopy();
mutable.addSpell(spellFromStele, spellLevel, /* locked = */ true);
ISpellContainer.set(steleStack, mutable.toImmutable());
```

**为什么 `locked = true`**：玩家右键忆碑"读取记忆"学到的法术，不应该能被随意丢掉 —— 这是"碑上刻的东西"。

### 6.2 忆晶（Memory Crystal）

忆晶是**货币/材料**，不是容器。它只是一个 `Item`，在铭刻台里当输入。

**建议给忆晶加一个可选的"封存"功能**（M5 之后）：玩家可以把一个法术封存进忆晶，做成"自制卷轴"。这用 `createScrollContainer` 实现，等价于给玩家一个自制的、可交易的记忆载体。

### 6.3 忆格上限的实现位置

**关键决策**：忆格（Engram Slot）**不要**做成 `ISpellContainer` 的 `maxSpellCount`。

理由：
- `ISpellContainer` 是**物品**的属性，忆格是**玩家**的属性。
- 忆格控制的是"玩家同时能持有几个记忆"，与"哪本书装几个法术"是两件事。

**正确实现**：忆格存在 `player.getPersistentData()` 里（见 `03_法术实现规范.md`），由你自己的管理器读写。法书/护甲的忆格加成在每次计算时读取装备并累加。

## 七、事件钩子

### 7.1 `InscribeSpellEvent`（✅ Forge 事件总线）

```java
public class io.redspace.ironsspellbooks.api.events.InscribeSpellEvent
        extends net.minecraftforge.event.entity.player.PlayerEvent {

    private final SpellData spellData;

    public InscribeSpellEvent(Player player, SpellData spellData);
    public SpellData getSpellData();
    public boolean isCancelable();   // ⭐ 可取消
}
```

**忆海的用法**：

```java
@SubscribeEvent
public void onInscribe(InscribeSpellEvent event) {
    SpellData data = event.getSpellData();
    if (!data.getSpell().getSchoolType().getId().getNamespace().equals("mnemosyne")) return;

    // 例：铭刻忆海法术时，检查玩家是否有足够"记忆承载力"
    int currentLoad = MnemosyneData.getMemoryLoad(event.getEntity());
    int maxLoad = MnemosyneData.getMaxMemoryLoad(event.getEntity());
    if (currentLoad + 1 > maxLoad) {
        event.setCanceled(true);
        event.getEntity().displayClientMessage(
            Component.translatable("mnemosyne.msg.memory_overload"), true);
    }
}
```

**注意**：`InscribeSpellEvent` 继承 `PlayerEvent`，所以用 `event.getEntity()` 拿玩家。

### 7.2 其他相关事件（实测清单）

| 事件 | 用途 |
|---|---|
| `SpellOnCastEvent` | 记录"最后施放的法术"（忆海的核心机制之一） |
| `SpellPreCastEvent` | 施法前拦截（可取消）—— 用于"记忆混乱导致施法失败" |
| `ModifySpellLevelEvent` | 动态修改法术等级 —— ⭐ 可用于"共鸣"临时提升等级 |
| `SpellDamageEvent` | 记忆伤害的特殊处理 |
| `ChangeManaEvent` | 忆格惩罚（每格 +10% 蓝耗）的实现点 |
| `CustomizeScrollModNameEvent` | ⭐ 自定义卷轴 tooltip 的模组名 |
| `SpellCooldownAddedEvent` | 冷却相关 |

**⭐ `ModifySpellLevelEvent` 是共鸣机制的最佳落点**：

`01_核心机制_忆格系统.md` 里定义"共鸣：每占用 1 个忆格，记忆法术强度 +20%"。有两种实现：

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 改属性 | 动态给玩家加 `mnemosyne:memory_spell_power` 属性修饰符 | 简单，但会影响所有记忆法术（包括不该影响的） |
| **B. 改等级**（推荐） | 在 `ModifySpellLevelEvent` 里，如果法术是忆海的，`+1` 等级 | 干净，只在施法瞬间生效，走官方的等级→强度公式 |

方案 B 的伪代码：

```java
@SubscribeEvent
public void onModifyLevel(ModifySpellLevelEvent event) {
    if (!(event.getEntity() instanceof Player player)) return;
    if (!event.getSpell().getSchoolType().getId().getNamespace().equals("mnemosyne")) return;

    int engrams = MnemosyneData.getUsedEngrams(player);
    if (engrams > 0) {
        event.addLevel(1);   // 共鸣：+1 等级
    }
}
```

⚠️ **必须验证 `ModifySpellLevelEvent` 的确切方法名**（`addLevel` / `setLevel` / `getLevel`），M1 阶段用 IDE 自动补全确认。本文件基于 javap 的方法签名，但 `javap` 未展开该事件的完整方法列表。
