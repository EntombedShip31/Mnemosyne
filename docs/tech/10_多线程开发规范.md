# 10 · 多线程开发规范

> 本文件是 `mnemosyne`（忆海 / 记忆·认知流派）技术文档集的第 10 篇。
> 目标：让**多个 AI 会话（或多人）同时开发**这个模组，而不互相踩脚、不产生冲突、不重复劳动。
> 配套：`11_提示词库.md`（可直接复制的提示词）。

---

## 〇、三条铁律

并行开发失败的原因**永远**是同一个：**两个人同时改同一个文件**。
所有规则都是为了防这一件事。

### 铁律一：一个文件只有一个主人

**任一时刻，一个文件只能有一个工作流在写。**

```
✅ WS-C 拥有 spell/base/*.java      → 只有 WS-C 能改
❌ WS-D1 想给 EncodeSpell 加个方法  → 必须走「接口变更申请」（§五）
```

### 铁律二：接口先冻结，实现后并行

**并行开始前，所有跨工作流的接口签名必须写进文档并冻结。**

```
冻结的东西：类名、public 方法签名、NBT 键名、注册 ID、事件名
不冻结的：  方法体、私有字段、内部算法
```

冻结后，WS-D 可以放心地 `new MemoryArrowSpell()`，即使 WS-C 还没写完基类
（先用 stub，能编译就行）。

### 铁律三：集成点必须串行

**每个阶段的末尾有一个"集成检查点"，必须由单一线程完成。**

```
Phase 2 的四个工作流各自完成
        ↓
   [集成检查点] ← 单线程：合并、编译、跑通冒烟测试
        ↓
Phase 3 才能开始
```

**不要跳过集成检查点。** 四个"各自能编译"的分支合起来编译不过，是并行开发的常态。

- **WS-D1/D2/D3 天然三分**，因为它们拥有不同的目录，且都只依赖 WS-C。

## 二、开发进程顺序（五阶段）

```
Phase 0 ──► Phase 1 ──► Phase 2 ──► Phase 3 ──► Phase 4
  1 线        3 线         4 线         4 线        1 线
```

### Phase 0 · 地基（1 线，串行）

| 工作流 | 产出 | 验收 |
|---|---|---|
| **WS-0** | 能编译、能启动的空壳模组 | `./gradlew runClient` 进主菜单，模组列表显示"忆海 · Mnemosyne" |

**为什么必须串行**：`build.gradle` / `mods.toml` / 主类是所有东西的前提。
任何人此时动它们都会造成混乱。

**参考**：`07_1.20.1Forge模组开发指南.md` §2~§5 是逐字可用的配置。

**出口条件**：`./gradlew build` 成功 + `runClient` 能进游戏。

---

### Phase 1 · 扇出（3 线并行）

| 工作流 | 内容 | 为什么现在做 |
|---|---|---|
| **WS-A** ⭐ | 学派 + 2 属性 + 忆晶物品 + 音效注册 + lang + 伤害类型 | **关键路径**，所有下游都等它，单独一条线全力做 |
| **WS-H** | 全部美术贴图（脚本生成 + 手绘） | **零依赖**，越早开始越好 |
| **WS-G1** | 世界生成的全部 JSON（结构/放置/模板池/处理器/群系标签/战利品表） | **零依赖**，纯 JSON，不需要游戏能跑 |

**⚠️ Phase 1 的 WS-G1 只能做 JSON 部分。**
遗迹的 `.nbt` 结构文件必须在游戏里用结构方块导出（见 `06_世界生成.md` §4），
所以要等 Phase 0 的空壳能启动。那部分归 Phase 2 的 WS-G2。

**出口条件**：
- WS-A：`/attribute @s mnemosyne:memory_spell_power get` 返回 `1.0`，创造模式物品栏能看到忆晶
- WS-H：13 张贴图全部就位，游戏里无紫黑格
- WS-G1：`/locate structure mnemosyne:memory_ruin` 能返回坐标（此时结构体是空的，只有连接点）

**→ [集成检查点 1]**：单线程合并，确认 `./gradlew build` 通过、`runClient` 无 ERROR。

---

### Phase 2 · 骨架（4 线并行）

| 工作流 | 内容 |
|---|---|
| **WS-B** | 忆格数据层（`getPersistentData()` 读写、腐坏计时、共鸣计算） |
| **WS-C** | 四个法术基类 + `LongCastTracker` |
| **WS-G2** | 在游戏内用结构方块制作遗迹 NBT，导出到 `structures/` |
| **WS-H2** | 剩余美术（护甲 UV、方块贴图、忆碑模型） |

**⚠️ WS-B 和 WS-C 必须在 Phase 2 完成**，因为 Phase 3 的 6 条线全都依赖它们。

**出口条件**：
- WS-B：能写入一个假忆格，`/data get entity @s` 能看到 NBT，120 秒后自动消失
- WS-C：四个基类能编译，各有一个可实例化的 stub 子类
- WS-G2：遗迹在游戏里完整生成（有房间、有宝箱）
- WS-H2：全部贴图就位

**→ [集成检查点 2]**：单线程合并 + 冒烟测试（能生成遗迹、能写入忆格）。

---

### Phase 3 · 主体（4 线并行）

| 工作流 | 内容 | 工作量 |
|---|---|---|
| **WS-D1** | 8 个低阶法术 | 中 |
| **WS-D2** | 4 个中阶法术 | 中 |
| **WS-E** | 遗忘系统（**全项目最大工程量**，32 生物映射） | **大** |
| **WS-F** | 卷轴物品 + 忆海法书 5 等级 + 铭刻事件 | 小 |

**⚠️ WS-D3（高阶法术）不放这里**，因为它依赖 WS-B（忆格）的最终接口，
而高阶法术（记忆掠夺/忆海/千忆归一）是忆格系统的最重使用者。
放到 Phase 4 更稳。

**出口条件**：每个法术能施放、能造成伤害、能触发音效。

**→ [集成检查点 3]**：单线程合并 + 用 `/give` 拿到 12 个法术卷轴逐个实测。

---

### Phase 4 · 收尾（4 线并行）

| 工作流 | 内容 |
|---|---|
| **WS-D3** | 6 个高阶法术（含三个长吟大招） |
| **WS-I** | HUD（忆格条、共鸣指示、腐坏倒计时、长吟期选择列表） |
| **WS-J** | 遗迹方块（忆碑、忆晶簇）+ 忆魇实体 |
| **WS-E2** | 遗忘系统的 BOSS 免疫与降级路径 |

**→ [集成检查点 4]**：单线程合并 + 完整流程测试。

### Phase 5 · 平衡与发布（1 线，串行）

| 内容 | 依据 |
|---|---|

## 五、接口变更申请协议

当你发现**必须**修改别人拥有的文件时，不要直接改。走这个流程：

```
1. 停下来，不要动那个文件
2. 在汇报里写清楚：
   - 你想改哪个文件的哪个签名
   - 为什么现有签名不够用（举出具体用例）
   - 你的建议改法
   - 这个改动会影响哪些其他工作流
3. 由集成者（Phase 末尾的单线程）决定：
   - 批准 → 由文件主人改，或授权你改
   - 拒绝 → 给出替代方案
```

**为什么这么严**：并行开发的成本几乎全部来自"合并冲突"和"接口漂移"。
一个签名的改动会连锁影响 4 个下游工作流，代价远大于多花 10 分钟沟通。

**允许的"无申请"变更**（不涉及跨工作流契约）：
- 方法体内部逻辑
- 新增 `private` 方法
- 新增 `private` 字段
- 修改注释与日志

`spell/low|mid|high/` 的 18 个 stub 类**都已写好**，数值取自 `tech/04`。
WS-D1/D2/D3 现在只需要填自己那个 stub 的 `onCast(...)` 方法体。

**⭐ 一个必须知道的过渡状态**：这 18 个 stub 目前是 `extends AbstractSpell`（ISS 的类），
**不是** `tech/11` §八 表格里写的 `EncodeSpell` / `OblivionSpell` / `MnemosyneProjectileSpell` / `MnemosyneLongCastSpell` ——
因为那四个基类属于 WS-C，是 **Phase 2** 的产出，Phase 1 时还不存在。

```
Phase 1（已做）  stub extends AbstractSpell        ← 能编译、能注册、能进游戏
Phase 2（WS-C）  交付 spell/base/*.java 四个基类
Phase 3+（WS-D） 把 extends 换成对应的 WS-C 基类    ← 只改 extends 一行，构造器与数值不动
```

**每个 stub 的类注释里都写清了自己将来该继承哪个基类**，WS-D 照做即可。

## 八、汇报格式（统一，便于集成者快速核对）

```markdown

|---|---|---|---|

| 2 | <游戏内验证> | ✅ | <现象描述> |

### 接口变更申请（如有）
```

**"证据"是必填的。** 写"✅ 测试通过"不算，要写"`/attribute @s mnemosyne:memory_spell_power get` 返回 `1.0`"。

## 九、反模式清单（不要做的事）

| 反模式 | 为什么有害 | 正确做法 |
|---|---|---|
| 两个工作流同时改 `MnemosyneMod.java` | 必然冲突 | 主类只在 WS-0 改；其他工作流用 `@Mod.EventBusSubscriber` 自动注册 |
| 为了"方便"把工具类放在公共包里大家一起改 | 公共包会成为冲突热点 | 工具类归属明确（`LongCastTracker` 归 WS-C） |
| 并行前不冻结接口 | 后期大规模返工 | Phase 1 末尾冻结全部签名 |
| 跳过集成检查点 | 四个分支合起来编译不过 | 每阶段末尾单线程集成 |
| 让 WS-D1/D2/D3 共用一个文件放公共逻辑 | 三个工作流抢一个文件 | 公共逻辑上提到 WS-C 的基类 |
| 一个工作流"顺手"改了别人的文件 | 集成者无法判断改动来源 | 走接口变更申请 |
| 把 `docs/` 里的 API 结论当成"可以改的注释" | 那些是实测结果，改了就是错的 | `docs/tech/01` 是只读的事实基准 |
