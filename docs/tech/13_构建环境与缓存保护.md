### 2.4 ⭐ MC 反编译管线为什么必须跑 10~40 分钟（逐步拆解）

#### 先回答一个常见疑问：为什么非得反编译？jar 不就是个压缩包吗？

**jar 确实是压缩包，但这里要做的不是"压缩"，是"编译"；而且要打包的不是 Minecraft。**

**① 我们的产物 jar 里没有 Minecraft。**
`build/libs/mnemosyne-0.1.0.jar` 只有 ~370 KB / 38 个类，全是 `com/etbs31/mnemosyne/**`。
Minecraft 留在游戏安装目录里，永远不会进我们的 jar。

**② 编译需要一个"名字对得上"的 MC。**
我们的源码写的是：

```java
target.hurt(spell.getDamageSource(caster), amount);
if (entity instanceof Mob mob) { mob.goalSelector.getAvailableGoals(); }
```

javac 必须去某个 jar 里**按名字找到** `getDamageSource`、`goalSelector`。
但 **Minecraft 官方发行的是混淆过的字节码** —— 那个方法在官方 jar 里叫 `m_7307_`（SRG）
或 `b`（混淆），**对不上**，编译会直接报"找不到符号"。

所以必须有一个**名字已经还原成人类可读**的 MC jar。那个 jar 只能**本地生成**。

**③ 为什么不能直接下载一个"已经反编译好的"？—— 法律，不是技术。**
Mojang 的 EULA 不允许再分发 Minecraft 的代码（源码或反编译产物都不行），
Mojang mappings 也有自己的许可。
**所以任何人都不能把"反编译好的 Minecraft"放到服务器上。**
Forge 只能发布**补丁** —— 补丁里只有"增删了哪几行"，不含完整的 MC 代码。

**④ Forge 恰恰是靠"给 MC 源码打补丁"工作的。**
这一点可以直接验证：解包 `forge-1.20.1-47.4.0-userdev.jar`，里面装着

```
config.json
joined.lzma
patches/**/*.java.patch     ← 658 个
```

补丁长这样（逐字，来自 `patches/com/mojang/blaze3d/pipeline/RenderTarget.java.patch`）：

```diff
--- a/com/mojang/blaze3d/pipeline/RenderTarget.java
+++ b/com/mojang/blaze3d/pipeline/RenderTarget.java
@@ -113,7 +113,10 @@
+         if (!stencilEnabled)
              GlStateManager._texImage2D(3553, 0, 6402, this.f_83915_, ...);
+         else
+            GlStateManager._texImage2D(..., GL30.GL_DEPTH32F_STENCIL8, ...);
```

**是标准 unified diff，目标是 `.java` 文件。** 要应用它，你必须先有 `.java` 文件。

**⑤ 于是整条链路是被逼出来的：**

```
下载混淆 jar
  → 反编译成 .java            （decompile，5~20 min，单核）
  → 应用 658 个源码补丁        （patch）
  → 重新编译回 jar            （recompile，3~15 min，单核）
  → 重命名到 official 映射     （rename / createSrgToMcp）
  → 应用 AccessTransformer    （把 goalSelector 这类成员提升为 public ——
                              这就是为什么我们能直接访问它，见 docs/tech/03 §7.2）
```

> **一句话**：你要照着说明书拧螺丝，但厂家只卖**没有刻度的毛坯螺丝刀**，
> 而且**不允许任何人卖"刻好刻度的"**。所以你只能自己刻一次刻度 ——
> 刻完之后所有活都能用（缓存），**但只要刻度被擦掉，就得重新刻**。

#### 步骤清单与耗时

ForgeGradle 把这条链路拆成一串**独立缓存步骤**，任一步的产物缺失，
**它和它之后的所有步骤都会重跑**。日志里能看到它们逐个打印：

```
Setting up MCP environment
Initializing steps
Executing steps
 > Running 'downloadManifest'   > Running 'downloadJson'
 > Running 'downloadClient'     > Running 'downloadServer'
 > Running 'extractServer'      > Running 'downloadClientMappings'
 > Running 'mergeMappings'      > Running 'stripClient'
 > Running 'stripServer'        > Running 'merge'
 > Running 'listLibraries'      > Running 'rename'
 > Running 'decompile'          ← ⭐ 大头 1
 > Running 'recompile'          ← ⭐ 大头 2
 > Running 'inject'  > Running 'patch'  > Running 'AccessTransformer'
```

| 步骤 | 在干什么 | 耗时 | 瓶颈 |
|---|---|---|---|
| `download*` / `mergeMappings` / `strip*` / `merge` / `listLibraries` | 下载客户端+服务端、合并成 joined jar | 1~3 min | **网络**（本机走代理 `127.0.0.1:58814`） |
| `rename` | 整个 jar 的字节码重命名 | 1~3 min | I/O |
| **`decompile`** | **ForgeFlower 反编译整个 MC** | **5~20 min** | **单核 CPU** |
| **`recompile`** | **javac 重新编译约 1 万个生成的 `.java`** | **3~15 min** | **单核 CPU** |
| `inject` / `patch` / `AccessTransformer` | 打补丁 | 2~5 min | I/O |

**核心原因：`decompile` 与 `recompile` 都是单线程的。**
1.20.1 的 joined Minecraft 大约 **3 万个 class / 200 MB 字节码**；
ForgeFlower 是 FernFlower 的 Forge 分支，**ForgeGradle 不做并行** ——
**机器有多少核都没用**，这两步就吃掉 10~35 分钟。

#### 怎么判断"在跑"还是"卡死了"

```bash
# 当前在第几步（最后一条就是）
grep "Running '" ~/.gradle/daemon/8.8/daemon-<pid>.out.log | tail -1
# 日志还在不在更新
ls -la --time-style=+%H:%M:%S ~/.gradle/daemon/8.8/daemon-<pid>.out.log
```

- ⚠️ **`decompile` 期间日志会长时间"冻住"**，没有任何逐类进度输出。
  **这是正常的，不是死机 —— 千万别 Ctrl+C**（一按就全白跑，下次还得从头来）。
- ⚠️ **超过约 45 分钟没动静** → 大概率不是真在算，而是**并发构建在抢
  ForgeGradle 的缓存锁**（见 §一 第 2 条）。这时该做的是**关掉多余的构建**，
  而不是杀掉正在跑的那个。

#### 时间估算

| 场景 | 预计 |
|---|---|
| 只有 1 个构建在跑 | **10~20 min** |
| 同时有 2 个构建在跑 | **25~45 min**（互相抢锁，接近串行） |
| 之后的所有构建 | **秒级**（缓存命中，不再重跑） |

> 结论：**这一次的等待只买一次单。** 只要 `~/.gradle/caches/forge_gradle` 不再被删，
> 以后构建都是增量的。反过来说 —— **任何"清理 Gradle 缓存"的动作都等于
> 让下一次构建白等 10~40 分钟**，这就是 §一 那条红线的由来。

### 2.5 ⭐ 为什么以前构建"一下就下好了"（最容易被误解的一点）

**"下载 Gradle" 和 "反编译 MC" 是两件完全不同的事，前者从来不是瓶颈。**

| | 是什么 | 耗时 | 缓存在哪 |
|---|---|---|---|
| **下载 Gradle 发行版** | 从腾讯镜像下一个约 130 MB 的 zip | **几分钟**（国内镜像） | `~/.gradle/wrapper/dists/`（本机 589 MB / 7 个版本） |
| **反编译 MC** | **本地 CPU 计算**（ForgeFlower + javac），**跟下载完全无关** | **10~40 分钟** | `~/.gradle/caches/forge_gradle/` |

**为什么以前那么快**：`forge_gradle` 是**机器级共享的一次性缓存**。
这台机器上**任何一个** ForgeGradle 项目（例如 `D:\桌面\1.20.1forge模组开发`）
第一次构建时，已经付过那 10~40 分钟的成本，结果被**所有**同 MC+Forge+mappings 的项目共用。

**铁证**：本项目 2026-09-15 的首次构建日志里就有

```
> Task :extractSrg UP-TO-DATE
> Task :createMcpToSrg UP-TO-DATE
```

整次构建只用了 **27 秒**。如果反编译要重跑，绝不可能这么快
→ 说明当时缓存是**继承来的、热的**，我们项目从来没付过那笔钱。

所以：**豆包删掉 `forge_gradle/minecraft_user_repo/mcp/**` = 让这笔成本重新付一次。**
这不是"变慢了"，是"欠的账现在要还"。

### 2.6 ⚠️ 另一个会伪装成"在慢慢反编译"的故障：僵尸 daemon

`build/<构建日志>.log` 末尾如果出现：

```
Caused by: java.lang.IllegalArgumentException: Unexpected type tag 71 found.
	at org.gradle.internal.serialize.DefaultSerializerRegistry$TaggedTypeSerializer.read
	at org.gradle.internal.remote.internal.inet.SocketConnection.receive
```

那是 **Gradle 客户端 ↔ daemon 的 socket 协议不匹配**（序列化类型标签对不上），
典型成因是 daemon 注册表里混进了**僵尸或不兼容的 daemon**。

**它和"正在反编译"的表现一模一样**（日志静止、没有任何输出），但**等多久都不会好**。
判别方法：

```bash
# 1) 日志末尾有没有报错
tail -20 build/*.log
# 2) 日志里的 daemon PID，和真正存活的 java 进程对得上吗
#    ⚠️ 见 2.8：不要用 tasklist //FI，Git Bash 会把它吃掉，返回假空
tasklist /FO CSV | grep -i java
# 3) 那个 daemon 的 .out.log 最后写入时间
ls -la --time-style=+%H:%M:%S ~/.gradle/daemon/8.8/daemon-<pid>.out.log
```

**若某个 daemon 的 PID 不在存活列表里 → 它是僵尸注册项**，必须清掉再跑。

```bash
./gradlew --stop
# 若仍有残留：
rm ~/.gradle/daemon/8.8/registry.bin      # 只是 daemon 地址注册表，不是依赖缓存，删了无害
```

> ⚠️ 2026-09-19 复盘：上面这条"僵尸 daemon"判断**结论对但证据链不可靠**——
> 当时用来列进程的命令是坏的（2.8），"没有存活 java 进程"是假象。
> 真正让构建停住的是 **2.7 的 `listLibraries` 下载挂死**。两者都会表现为"日志静止"，
> 请先按 2.7 排查。

### 2.7 ⭐⭐ 真正卡住两次构建的元凶：`listLibraries` 下载挂死（2026-09-19 实测）

**症状**：日志停在

```
 > Running 'listLibraries'
```

之后再不前进，但**不是**在反编译（反编译会打印 `> Running 'decompile'`）。
两次构建（普通 daemon / `--no-daemon`）都死在同一步，各静默 20+ 分钟。

**定量判别（比"看日志有没有动"可靠得多）**：

```bash
# 1) 缓存还有没有新文件写入 —— 这是最硬的指标
find ~/.gradle/caches -type f -newermt "-3 minutes" | head
#   空 = 卡住了；有 = 还在下

# 2) 构建 JVM 的 CPU 增量（间隔 10 分钟取两次，差值 <5s = 阻塞而非计算）
#    用 PowerShell 工具（Bash 里调 PowerShell 会被拦）：
#      Get-CimInstance Win32_Process -Filter "Name = 'java.exe'" | Select ProcessId, UserModeTime, KernelModeTime
#    实测：11 分钟只涨 2.6 秒 CPU → 阻塞

# 3) 卡在哪条连接上
#      Get-NetTCPConnection -OwningProcess <构建JVM的PID>
#    实测：一条 Established 到 164.152.23.25:443，无进展
```

**根因**：`listLibraries` 要按 `version.json` 下 ~88 个 MC 运行库到
`~/.gradle/caches/forge_gradle/maven_downloader`。这些 jar 在 09-19 的误删中一并没了，
于是走网络重下；本机代理链路会在某条连接上**无限挂住**（Gradle 不读
`http_proxy`/`https_proxy` 环境变量，也没有默认 socket 超时）。
注意：**用 `curl` 带超时去下同一批文件是秒回的** —— 网络本身没问题，是 Gradle 那条连接挂了。

**解法（不碰网络，秒过）**：用 PCL2 本地已装好的库直接喂缓存。
`maven_downloader` 的布局 `group/path/name/version/file.jar`
和 `.minecraft/libraries/` **完全一致**，`.md5` 文件内容就是该 jar 的 32 位 md5 明文。

```bash
python tools/seed_mc_libraries.py     # 脚本已入库（tools/ 下，不会被 build/ 清理带走）
# 输出示例：声明 88 / 已存在 75 / 从 PCL2 拷入 11 / 补写 .md5 0 / 仍需联网 2
```

剩下极少数 PCL2 也没有的（实测是 `lwjgl-jemalloc-natives-macos`、`lwjgl-natives-linux`），
**用 `curl` 定向补**，别让 Gradle 去下：

```bash
curl -sS --connect-timeout 15 --max-time 90 -o <缓存目标路径> https://libraries.minecraft.net/<相对路径>
# 下完务必 sha1sum 对一遍 version.json 里的 sha1，再补 .md5（重跑一次 seed_mc_libraries.py 即可）
```

补齐后重启构建，`listLibraries` 由 20 分钟挂死变成**秒过**。

### 2.8 ⚠️ Git Bash 会吃掉 `tasklist //FI`，产出致命假阴性

```bash
tasklist //FI "IMAGENAME eq java.exe" /FO CSV    # ❌ 永远返回空
tasklist /FO CSV | grep -i java                  # ✅ 正常返回 3 个进程
```

MSYS/Git Bash 会做路径转换，`//FI` 被当成路径吃掉 → 过滤失效、输出为空。
**后果**：用它判定"没有存活 java 进程"会得出完全错误的结论
（2026-09-19 实测：命令说"零个 java"，实际有 3 个且其中一个占 663 MB）。
凡是"进程是否存活"这类判断，**必须换一个独立手段交叉验证**（如 `grep -i java`、或看缓存写入时间）。

### 2.9 dev 服务端/客户端启动时会重下 3500+ 个原版资源（同一套路第二次）

`runServer` / `runClient` 起来后会先 `Downloading: resources.download.minecraft.net … Asset: minecraft/sounds/…`，
同样因为 Gradle 不走代理而大量 `SocketTimeoutException`（实测 7 分钟才下一部分）。

位置：`~/.gradle/caches/forge_gradle/assets`（`indexes/5.json` 就是 1.20.1 的资源索引）。
PCL2 的 `assets/` 布局与它一致（`objects/<哈希前两位>/<哈希>`）：

```bash
python tools/seed_mc_assets.py
# 输出：索引 3575 个对象 → 已有 3533 / 从 PCL2 拷入 42 / 仍需联网 0
```

补齐后重启，下载量为 0，直接进服。

> ⭐ 与 2.7 是同一套思路，值得单独记住：
> **凡是 Gradle 要走网络的地方，先看本机有没有现成副本，按布局喂进缓存。**

**各目录体积与"能不能离线秒回"**（2026-09-19 实测，总计 1.1 GB）：

| 目录 | 大小 | 误删后能离线补回吗 |
|---|---|---|
| `assets` | 629 MB | ✅ 能从 PCL2 补（`seed_mc_assets.py`） |
| `maven_downloader` | 91 MB | ✅ 能从 PCL2 补（`seed_mc_libraries.py`） |
| `mcp_repo` | 173 MB | ❌ 反编译管线中间产物 |
| `minecraft_repo` | 53 MB | ❌ |
| **`minecraft_user_repo`** | **71 MB** | ❌ **这就是那 10~40 分钟的反编译产物，最值钱** |
| `deobf_dependencies` | 18 MB | ❌ |

## 三、修复步骤

> ⚠️ **一次只跑一个构建。** 多会话同时 `./gradlew build` 会互相锁死（见 §二 2.2 第 3 条）。
> 跑之前先确认没有别的会话在构建。

```bash
cd D:\桌面\铁魔法全新流派mod

# 1) 停掉所有卡住的守护进程
./gradlew --stop
```

## 五、常见问题：能把 Gradle 依赖缓存搬到 D 盘吗？

**结论：技术上可以，但这台机器上不建议。**

### 5.1 先看数据（2026-09-19 实测）

```
~/.gradle 总计                    1.3 GB
  ├── wrapper                     589 MB   ← 最大的一块（躺着 7 个 Gradle 版本）
  ├── caches                      407 MB
  │     ├── forge_gradle          232 MB   （MC/MCP 缓存）
  │     ├── modules-2             110 MB   （依赖 jar）
  │     └── 8.8                    66 MB
  ├── jdks                        222 MB   ← ⚠️ 全是废的（两个卡死的 .part）
  └── daemon                       47 MB   （日志）
```

盘剩余：**C: 26 GB（84% 满）／ D: 24 GB（93% 满）**

### 5.2 为什么不建议

1. **省不了空间，反而更紧。** 整个 `~/.gradle` 只有 **1.3 GB**，
   而 **D: 的剩余（24 GB）比 C:（26 GB）还少** —— 搬过去等于把压力挪到更紧张的盘。
2. **搬动 = 再预热一次。** 除非用「移动」而不是「复制」，否则 Gradle 看到空缓存 →
   重下 300+ 文件 + 重新反编译 MC。**你们已经因为缓存丢过一次，吃过 30 分钟的亏。**
3. **会引入一个更难查的新失败模式。** `GRADLE_USER_HOME` 必须让**每一个**调用 Gradle 的
   进程都看到。你同时跑多个 AI 会话 —— 只要有**一个**会话没继承到，它就会去用 C: 上的
   空缓存，表现是"怎么又要重下/怎么又变慢了"，而且极难定位到"是环境变量没传进去"。
4. **换位置解决不了真实痛点。** 你们的问题是「缓存被删」和「多会话抢锁」，
   这两个换到哪个盘都一样。

### 5.3 真要省空间，按性价比排序

| 优先级 | 动作 | 能省 | 风险 |
|---|---|---|---|
| ⭐ 1 | 删 `~/.gradle/jdks/*.part` + `*.lock` | **222 MB** | **零**（本来就是卡死的废下载） |
| ⭐ 2 | 删 `~/.gradle/daemon/*/*.log` | 47 MB | **零**（纯日志） |
| 3 | 删 `~/.gradle/wrapper/dists` 里**本项目不用**的版本（我们只用 **8.8**，那里还躺着 8.5 / 8.9 / 9.2.0 / 9.2.1 / 9.3.1 / 9.5.1） | ~400 MB | 低，但先确认别的项目不用那些版本 |
| 4 | 清 `~/.gradle/caches/*/tmp` | 视情况 | 零 |
| — | **搬 `~/.gradle` 到 D:** | 1.3 GB | **高**（见 §5.2） |

**真正的大头不在 `~/.gradle`。** 要腾空间应该去看：
`D:\PCL2`（MC 实例 + 存档）、`C:\Users\Etbs31\AppData`、以及各项目里的
`build/` `run/` `run-server/` `node_modules/`。
本项目里就有：`build/` 49 MB（含 60+ 个其他会话留下的临时文件）、
`run-server/` 16 MB（跑过的存档）、`可以参考的模组/` 36 MB。

### 5.4 如果将来一定要搬，四条硬要求

1. 用**用户级系统环境变量** `GRADLE_USER_HOME`（`setx`），**不要**用命令行 `-g` ——
   每次都要敲，一定会漏，一漏就变成"两个缓存各用一半"。
2. **移动**而不是复制：`robocopy <源> <目标> /E /MOVE`，保证缓存不重新预热。
3. 搬之前 `./gradlew --stop`；搬之后**重启所有 AI 会话 / IDE**，否则老会话还在写老位置。
4. 搬完验证两件事：新位置有 `caches/modules-2` 与 `caches/forge_gradle`；
   老位置 `~/.gradle` 已空。目标盘必须是**本地 SSD** —— 机械盘或外接盘会让构建明显变慢。

> Gradle 官方**只支持**通过 `GRADLE_USER_HOME` 整体搬。
> 没有"只搬 `caches` 而把 `wrapper` / `jdks` / `daemon` 留在原地"的官方开关
> （网上流传的 `org.gradle.cache.dir` 是未公开属性，不要依赖它 —— 未公开 = 随时可能变）。

### 6.5 手法备忘（下次清理由此照做）

- 本沙箱的 `rm` 是 **bash 函数**，转发到 `safe-delete-broker-delete.cjs` → 小批量用它就是安全路径。
- ⚠️ **别用 `find ... -delete` 或 `xargs rm`** —— 会绕过函数，变成真正的永久删除。
- ⚠️ **单次 `rm` 不要超过约 50 个文件**：代理逐文件起进程，161 个会超时被 SIGTERM 且**一个都没删掉**（实测踩到）。分 50 个一批 + 显式加长 `timeout`。
- 目录批量处理用 `mv`（不是 `rm`）：即时完成、天然可逆、没有批量限制。
- 清理前先 `du -sh` 记下体积，清理后**复查 `caches/modules-2` 的 jar 数没变**。

## 九、⭐ 打包 jar · 标准作业流程（SOP）

> 2026-09-19 实际走通一遍后整理的。**正常情况全流程 3~5 分钟**；
> 只有缓存被清掉时才需要 §2.7 的救急步骤（那次花了约 1 小时）。

### 9.1 三步前置（漏了会白打一次包）

```bash
# ① 一次只跑一个构建 —— 多会话并发会抢 ~/.gradle/caches/8.8/ 的锁，后到者静默阻塞
tasklist /FO CSV | grep -i java          # 有输出 = 有人在构建，等
#    ⚠️ 不要用 tasklist //FI ... ，Git Bash 会把它当路径吃掉，永远返回空（§2.8）

# ② 确认代码是最新的 —— 09-19 踩过：14:50 打完 jar，15:10 才有人提交，jar 白打
git status --porcelain
git log --format="%h %ad %s" --date=format:"%H:%M" -3

# ③ 跑自检（纯 stdlib，约 6 秒；CI 里也在 Gradle 之前跑）
python tools/check_resources.py       # 424 项，FAIL 必须为 0
python tools/check_spell_numbers.py   # 147 项，总表数值 ↔ Java 实现
python tools/check_particle_budget.py # 65 项，粒子预算
```

### 9.2 构建

```bash
./gradlew build -x copyToMinecraftMods --no-daemon --console=plain
```

- `-x copyToMinecraftMods`：不往 PCL2 的 `mods` 目录塞东西。想直接装进游戏就去掉它。
- `--no-daemon`：这台机器上常有别的会话跑 Gradle，daemon socket 容易被连坏（§2.6）。
- **不要用 `--rerun-tasks`**（会强制重解析全部依赖）。

产物：`build/libs/mnemosyne-<version>.jar`。

### 9.3 验证产物（必须做，`BUILD SUCCESSFUL` 会骗人）

```bash
# ① compileJava 是真的执行了，而不是 UP-TO-DATE（假绿灯）
grep -E "^> Task :compileJava|actionable" build/build_*.log

# ② jar 是重混淆后的生产包，不是开发态 mojmap 包
python -c "
import zipfile,re
z=zipfile.ZipFile('build/libs/mnemosyne-0.1.0.jar')
cls=[n for n in z.namelist() if n.endswith('.class')]
blob=b''.join(z.read(c) for c in cls[:40])
print('classes:',len(cls),' SRG refs:',len(re.findall(rb'm_[0-9]{3,}_',blob)))
"
#    SRG refs 有几百 = 已重混淆 ✅；为 0 = 拿到的是未重混淆的 dev 包 ❌
```

### 9.4 冒烟测试（`build` 查不出来的失效只能靠它）

```bash
./gradlew runServer --no-daemon --console=plain   # run-server/eula.txt 需为 eula=true
grep -E "Done \(" build/runserver_*.log           # 看到 Done (x.xxxs)! 即启动成功
```

**判别基线（本项目的正常结果）**：
- ✅ **零 worldgen / 数据包解析失败** —— 解析失败会让存档直接加载不了，这是最该盯的一条
- ✅ 战利品表解析失败 2 条，全是 ISS 自己的（`chests/catacombs/crypt_loot`、`chests/citadel/citadel_tomes`）
- ⚠️ 旧存档可能报 missing registry entries：都是已删内容的历史残留（5 级法书 `spell_book_t1~t5`、`memory_stele_fragment`、3 个已删法术的音效）。Forge 自动移除并备份存档，**不是缺陷**
- ⚠️ `Missing data pack file/mnemo_probe` —— 旧 `level.dat` 残留的临时探针，无害

用完直接杀掉 java 进程即可。

### 9.5 卡住了怎么办（决策树）

```
日志停在某一行不动
├─ 停在 '> Running listLibraries'   → §2.7：下载挂死（最常见的坑）
│    └─ python tools/seed_mc_libraries.py 用 PCL2 本地库喂缓存，秒过
├─ 停在 'Configure project :'       → 有人在并发构建，等或 --stop
├─ 末尾有 'Unexpected type tag 71'  → §2.6：僵尸 daemon，--stop + 删 registry.bin
└─ 其他                             → 先用 §2.7 的三条定量指标判"卡住"还是"在算"
```

**定量判别（别只看日志有没有动）**：
1. `find ~/.gradle/caches -type f -newermt "-3 minutes"` → 空 = 卡住
2. 构建 JVM 的 CPU 增量，10 分钟 <5 秒 = **阻塞**（不是在计算）
3. `Get-NetTCPConnection -OwningProcess <pid>` → 一条 Established 无进展

### 9.6 打包之后

- ⭐ **缓存是热的时候做一次备份**（冷缓存拷回去照样要重跑反编译）。
  **在 PowerShell / cmd 里跑**（`%USERPROFILE%` 在 Git Bash 里不会展开）：

  ```bat
  robocopy %USERPROFILE%\.gradle\caches\forge_gradle D:\gradle_cache_backup\forge_gradle /E /R:1 /W:1
  ```

  实测：**3898 文件 / 1.02 GB / 1 分 17 秒 / 失败 0**。备份与源文件数完全一致。

  **恢复**（缓存再被误删时，一条命令，零网络）：
  ```bat
  robocopy D:\gradle_cache_backup\forge_gradle %USERPROFILE%\.gradle\caches\forge_gradle /E /R:1 /W:1
  ```

  > **为什么是完整备份而不是排除 `assets`（629 MB）**：虽然 `assets` 是唯一能离线秒回的大头
  > （见 §2.9 的体积表），但排除它就要依赖"PCL2 还在 + 脚本还在"两个前提。
  > 在"缓存刚被删、急着恢复"的场景下，**一条 robocopy 搞定**的确定性比省 629 MB 更值钱。
  > 脚本（`tools/seed_mc_*.py`）保留为第二条路，成本为零。
  >
  > 若磁盘真的吃紧，加 `/XD assets` 可压到约 400 MB，代价是恢复后跑 dev 服务端要再补资源。

- 客户端那两项只有实机能判：粒子密度手感、`Unable to load model`。
  把 jar 丢进 PCL2 实例的 `mods` 目录（ISS / irons_lib / Curios / GeckoLib / player-animator / Caelus 都要在）。
